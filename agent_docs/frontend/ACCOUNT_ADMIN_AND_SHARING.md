## Auth screen

- `/login` is one restrained, flat `max-w-[42rem]` auth workspace on the answer-paper canvas, not a marketing page, generic SaaS card, or tiny floating panel. Its identity header presents AIQSA and `Question → Search → Answer` as quiet product orientation; each sign-in, request-access, invite, verification, reset-request, reset-completion, and request-result mode owns the page's sole `<h1>`, orientation copy, primary action, and only the relevant secondary route.
- Normal sign-in shows neutral `Continue with Google` and/or `Continue with Yandex` links only when the server has both credentials for that provider. They preserve the same sanitized internal `next` destination and remain absent from invite, verification, and reset modes. OAuth cancellation, provider failure, disallowed/pending account state, or a conflicting provider binding returns to the clean login URL with one readable privacy-safe outcome; raw provider errors, codes, and tokens never render.
- First OAuth use attaches the external identity to the existing normalized-email `User`, so password and OAuth login reveal the same chats, groups, settings, and entitlements rather than parallel accounts. Google linking requires its verified email claim; Yandex linking uses the authenticated profile's default email under the server policy documented in `SECURITY.md`. Later sign-in follows the stable provider account id.
- When multiple proof parameters are present, active proof precedence is `verify` → `reset` → `invite`. Successful invite/verification/reset settlement and explicit return to ordinary sign-in retire that local proof and replace the current history entry without any consumed bearer parameter while preserving safe `next`, OAuth outcome, and fragment state. The same mounted view does not resurrect retired proof from unchanged props, but a genuinely new proof tuple activates its new mode. An initial OAuth callback outcome appears near the heading before the sign-in form so it remains visible on short/mobile viewports; password sign-in mutation feedback sits directly after the primary action and before its secondary routes, while other mutation feedback remains in document flow after its form.
- Sign-in, invite-acceptance, verification-password, and reset-password fields have a visible `Show password`/`Hide password` control. A normal access request collects no password; direct invite acceptance does. Toggling visibility never clears the value; switching modes returns it to concealed. Password help stays visible and the browser receives `current-password` versus `new-password` autocomplete semantics.
- Each mutation disables its active fields, visibility toggle, submit, and mode-navigation actions, and uses a specific working label/status such as `Signing in…` or `Updating password…`. Password sign-in owns one button-contained spinner and working label rather than duplicating progress below the form. The user cannot submit twice or replace the active mode while a request is pending.
- Local validation plus backend/network failures show readable sentences in an announced `role="alert"` while preserving the stable backend code in parentheses. Credential failures mark the attributable email and/or password fields invalid and associate them with the adjacent alert. A failed login, invite acceptance, allowlist check, SMTP configuration/send, verification, or reset attempt stays retryable in its current mode and preserves entered values where applicable. Initial password sign-in leaves focus under browser/user control during hydration; deliberate mode transitions and settled requests move focus to the first useful field.
- Normal access requests honor `verification_required` with a check-email result if a server supplies that status. The current server normally returns the intentionally generic `request_received` outcome, which never claims that an email was sent or reveals whether an account exists; allowlist denial, SMTP unavailability, and SMTP send failure remain on the form. Password-reset requests likewise say only that a link was sent if the account can reset.
- Invite links open `Create your account` directly and never render the raw token or ask the recipient to re-enter the invited email. The two-field form collects name plus a new password, submits them with the one-time token to direct invite acceptance, then uses the returned session cookie and safe `next` path to enter the workspace immediately; it has no check-email or second-sign-in state. Verification links remain the normal access-request path: they present the one-time new-password form, then distinguish active sign-in, pending-admin-approval, and generic invalid/error outcomes. Reset-completion links explain one-time use; success returns to sign-in and existing server behavior revokes prior sessions.
- The normal auth workspace never renders an access-token field, Bootstrap token action, recovery-route hint, or fake open-registration promise. Safe internal redirect normalization, route guards, account approval, verification, SMTP, and password policy remain server contracts rather than presentation choices.
- At 390x844 the workspace is top-aligned, uses `100dvh` plus safe-area padding, remains vertically scrollable when the software keyboard reduces space, keeps the current primary action reachable, and has no page-level horizontal overflow. At desktop widths through 720px height and at 844x390, Request access/invite registration use a compact two-field row followed by primary/secondary actions so the panel bottom, primary action, and `Back to sign in` are initially visible while labels/help remain intact and the page can still scroll. All approved palettes flow through semantic tokens and preserve browser-autofill contrast.

## Public share

- `/s/[shareToken]` remains anonymous and hashes the secret token before server lookup. The route passes only the stored public title and immutable sanitized snapshot into `PublicShareView`; missing, revoked, expired, or invalid links all use the same 404 `Shared snapshot unavailable` view with no reason, owner, token, or other private detail.
- A quiet workspace-rail header pairs AIQSA identity and `Shared research` context with an explicit `Read-only snapshot` marker. One wrapped `<h1>` names the shared chat, blank titles safely fall back to `Shared chat`, and one divided note explains that this fixed branch will neither update nor change the original.
- Shared questions use the private thread's compact right-aligned filled treatment; shared answers stay full-measure document flow on answer paper. There are no literal role labels, provider/model metadata, message actions, composer, Details, branch controls, share/revoke controls, calls to action, or authenticated-shell dependencies.
- Rendering consumes only the snapshot's user/assistant text blocks and the attachment-omission text produced by the existing sanitizer. Private message/share/run ids, attachment object ids/URLs, raw provider payloads, secrets, and user/group metadata are never read into the view. Safe links and citations already represented in sanitized Markdown remain usable; raw HTML and unsafe URLs remain inert through the shared `MarkdownMessage` renderer.
- Share creation rejects an active visible branch containing native Gemini grounded live-only provenance. The UI must report that the live-only result cannot be published; it never shares the neutral placeholder as if it were the answer or asks the browser to supply missing content.
- An empty snapshot has a deliberate no-visible-messages state; an individual empty turn has neutral fallback text. Neither empty nor unavailable states invent content or add a call to action.
- The public page uses the shared reading measure and semantic palette tokens at every viewport. Long titles, prose, URLs, tables, and fenced code stay within the page; only table/code owners scroll horizontally. Code highlighting/copy and Markdown heading offset match the private thread, while the page itself stays overflow-free at 390x844.

It never derives `Needs setup` merely from `enabled && !ready`. Persistent enablement is not repeated per server or per run outside this single aggregate control.
- Prompt library has one clear editor/library hierarchy. Its persistent workbench header owns `Back to chat`; the library header owns search and `New prompt`, and flat divided rows distinguish the preset being edited. A two-pane library/editor composition is allowed only when viewport width is at least 1024px **and** viewport height is greater than 512px. In that composition the library and editor are independent local scroll owners while their headers and the editor action footer remain fixed. Below either threshold the workbench shows exactly one task at a time—library list or editor—and the editor exposes `Back to prompts`; returning preserves the library query, selection, scroll position, and sensible focus continuity. The surface explicitly directs runtime selection back to Run setup and exposes no `Next run`/`Use` action.
- The editor keeps the persisted startup default secondary to content: one restrained `Default for new chats` row owns `Make default`, `Prompt identity` owns the reusable name, and `Instructions` owns required system plus optional developer text. `Duplicate` remains a visible direct secondary action; destructive `Delete` moves under `More`, retains default protection, and enters an explicit confirmation. Save/create is the single primary action in the persistent editor footer; pristine invalid new prompts keep Required metadata neutral until the draft actually changes. Long names and bounded instruction previews remain readable without repeating actions in every library row.
- Editor selection is not run selection. `Next run` is chosen only in the composer prompt picker or command palette; `Default for new chats` is the persisted startup fallback. Browsing, opening, editing, or changing the default applies nothing to the current composer. This is intentional even when the library was opened from Run setup.
- The editor derives `Saved`, new, dirty, invalid, and saving presentation from the shared prompt-settings draft. Name and system instructions are required; their Required metadata stays neutral while valid and uses the semantic critical/error token only with the associated missing-field error. Save/create is enabled only for a dirty valid draft while no mutation is pending, and fields/actions expose the pending state without losing their labels.
- Create, update, duplicate, and delete mutations use the prompt APIs. `Make default` uses the same serialized current-user settings coordinator as composer prompt selection, so two prompt-default intents cannot commit or reconcile out of order. Success keeps the optimistic catalog aligned with the decoded settings response; a failed default remains queued behind the workbench-scoped Retry action, while other prompt failures leave the catalog, next-run choice, and dirty editor intact and report a readable, dismissible notice below the workbench header.
- Prompt library distinguishes catalog loading/error, a search with no matches, and a genuinely empty library. Until the catalog is ready it mounts no editor or prompt mutation action and offers resource Retry on failure; independent Settings remains available through its own Account destination. A prompt mutation error scrolls the editor’s save/action region into the nearest visible position without discarding the draft.
- Dirty prompt edits cannot be silently replaced by `Back to chat`, compact `Back to prompts`, New, another editor selection, Duplicate, or any destination replacement. Those paths use the shared discard confirmation; deleting the dirty preset discards first and then enters the separate destructive delete confirmation.
- Unsaved personal MCP values use the same close/section discard protection. Once a server mutation or personal-value save starts, Settings blocks close and section replacement until that exact request settles; a confirmed discard cannot leave a supposedly discarded write running in the background.
- The default-for-new-chats prompt is visibly protected from deletion. Changing the default moves both the marker and protection; deleting a confirmed non-default prompt falls editor/next-run state back to the surviving default when necessary, while a failed delete preserves the prompt and draft.
- Settings keeps bounded-dialog focus, safe Escape/backdrop close, opener restoration, and the shell inert while open. Prompt library instead exits explicitly through the guarded `Back to chat` path, restores focus to its opener when that target still exists, and keeps the covered shell inert without rendering a scrim or exposing a backdrop target. A nested discard or delete confirmation makes its owning Settings dialog or Prompt workbench inert, owns focus until resolution, then restores focus to the invoking control or the nearest surviving equivalent. Any action that replaces one workspace with another resolves the current dirty state before opening the next.
- Settings > Appearance renders AIQSA (`aiqsa`, dark), Graphite (`graphite`, dark), Verdant (`verdant`, dark), Classic Dark (`classic-dark`, dark), Classic Light (`neutral`, light), and Paper (`paper`, light) in that registry order. Paper provides a soft monochrome, graphite-action treatment inspired by familiar conversation-product restraint without copying brand chrome. Every choice applies immediately. All widths use one calm divided comparison list with a compact semantic preview, description, and current selection; it never becomes a dashboard-like card grid.
- Theme selection is a local UI preference only: it persists in LocalStorage, mirrors to the same-site `aiqsa.theme` cookie, and the server validates that cookie to emit matching first-paint `data-theme` and `data-color-scheme`. `neutral` is the first-use fallback. On hydration a valid LocalStorage choice wins a stale cookie and repairs its mirror; malformed LocalStorage falls back to the already validated server-rendered theme and is repaired rather than forcing `neutral`. Runtime switching updates both attributes together so browser controls and rendered content agree. It is not synced to the user account, prompts, or conversations.
- Project settings labels its sole context field `Project instructions` and explains that the text is supplied to chats in that project. It retains modal focus, Escape, opener-restoration, and dirty-confirmation contracts; an inner confirmation owns focus and Escape before returning to the project dialog.

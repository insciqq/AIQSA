# FRONTEND COMPOSER AND CONTROLS

Owner: Research Chat interaction maintainers
Scope: Functional interaction contracts for composer, navigation, next-run controls, receipts, and Details; appearance remains in DESIGN_SYSTEM.md.

## Composer

- Enter sends.
- Enter does not send while an IME composition is active. One client-safe guard recognizes native/React composing state, `Process`, and legacy keyCode 229 across the composer, command palette, shared pickers, and inline chat/folder create/rename handlers; composed Enter/Escape never commits or cancels partial text.
- Shift+Enter inserts newline.
- The visible `Send` action keeps the stable label `Send`. It is disabled while streaming, while a blank workspace is creating its first persisted chat, or while empty with no staged attachments. In edit-branch mode, attachments alone are not sendable: edited text is required, and `Cancel edit` remains available in the branch strip.
- Composer input stays disabled until catalog and workspace/chat-detail bootstrap complete and whenever the current user has no entitled model. Loading, no-model, creation, and actionable disabled reasons render as status text in the composer frame.
- Send is disabled while uploads are in flight so a message cannot silently skip a staged file. The textarea remains draftable, the frame reports `Uploading…` as status/busy feedback, and file selection/drop is unavailable until the upload settles.
- The visible `Stop` action remains available while the active chat streams. It stays disabled with `Starting run…` until the client has the persisted model-run id needed to call the server cancel endpoint. Stop requests durable cancellation before aborting the browser stream or painting a cancelled tail; a losing cancel reconciles the returned current status instead of fabricating local cancellation.
- When another chat's response is still running, the current chat's composer can draft and send its own run; only the chat that already has an active stream is blocked from sending another run.
- Switching away from and back to a chat with an in-flight foreground stream preserves optimistic user/assistant rows and cached token deltas until the final `chat_update` canonicalizes the thread.
- Draft text, staged attachments, edit intent, pending send/upload generations, and operation feedback belong to one keyed in-memory composer session: a saved chat, the blank root, or a specific blank folder. Navigation only selects that key; it does not copy composer content through a singular active buffer.
- Reload/background-run resume polling distinguishes a found run, proven 404/not-found, and transiently unknown network/non-2xx/malformed reads. Unknown reads retain only that source chat's run gate and continue bounded backoff; at the horizon the gate remains until `Check run`, cancellation, navigation-owned exit, or a later proven terminal read, while other chats remain sendable.
- Refetched model-run Details state is always written to its explicit source chat key, including after navigation. The active-chat selector alone chooses what is rendered, so a slow run GET cannot paint stale events or usage into another chat and the source remains inspectable when revisited.
- Textarea auto-grows to 200px max.
- The whole composer is centered and capped at `max-w-reading` (46rem). Edit/disabled strips, attachments, textarea, controls, context/usage, and actions all stay inside the same frame rather than stretching independently across the thread pane. At no more than 42rem viewport height, padding, attachment space, textarea minimum/maximum height, and trailing receipt space use the short-height density while preserving the same control owners and touch targets.
- A ready blank workspace (`activeChatId = null`) centers that one composer and its short orientation copy in the available conversation stage. Its prompt-first variant hides empty-conversation Share/Details/menu actions, visually suppresses the context gauge, and keeps the same direct Model/Profile/Search plus More controls without changing their underlying owner. As soon as first-chat creation begins, a saved chat owns the session, or any optimistic/persisted message exists, the same mounted composer moves to the thread tail and the normal conversation actions return. Loading, error, no-model, saved-empty, and active/history states keep their existing truthful bottom placement; there is never a second composer or draft owner.
- The draft has one distinct bounded `Message` plane at every viewport. Its `Message` label remains available to assistive technology but is visually suppressed in blank and active-chat states; `Ask AIQSA…` remains visible guidance. Below `sm`, or at no more than 32rem viewport height, an empty idle thread-tail composer may collapse to that Message row after a recent real wheel/touch gesture and 48px of consecutive movement in either direction. Direction reversal resets accumulation; programmatic anchoring and Latest do not qualify. Message click or keyboard/programmatic focus expands it. Draft text, staged attachments, upload/edit work, actionable error/unavailable state, chat/breakpoint change, and a streaming run without a persisted id force expansion; an addressable streaming run keeps a labeled Stop beside Message while collapsed.
- The normal thread-tail footer contains a direct model picker, one current-value Profile picker, Search, a More action for the complete Run setup, a labeled Tools entry, one circular context gauge, Attach, and Send/addressable Stop. The model picker keeps provider/model identity but omits the redundant visible `Model` prefix. The Tools entry follows the selected catalog model's `toolCalling` capability: an unsupported model states `Not supported by this model`, and send/regenerate explicitly suppress persisted MCP tools for that run without changing server enablement. Periodic and visibility-owned MCP background refresh preserves the last rendered Tools lifecycle/text/icon—including a ready configured-empty state—until a successful replacement arrives, so refresh remains live without loading-state flicker. The centered blank variant keeps those same owners and omits the gauge until the conversation starts. The direct controls wrap as space narrows rather than disappearing behind More. The gauge uses the safe input budget—not the provider's total context—as its denominator and opens the single disclosure for approximate input, safe input budget, total model context, active-branch messages, and matching provider-reported usage rather than creating another resting status line.
- Draft text, attachments/uploads, edit work, actionable errors/unavailable states, and streaming cancellation all render within that same composer. Stop remains visible while streaming and stays disabled with `Starting run…` until the persisted run id exists.
- Attachment chips support uploaded PDFs, images, and text-like documents. Text-like documents remain available to every selected catalog model because they become extracted provider text; PDF availability follows `documentInputMode`, and images follow `imageInput`. A PDF whose bounded extraction is `partial` with retained text stays sendable and shows per-file caution that only the available text will be used. The valid zero-emitted `partial` edge states that no complete PDF text fit within the configured limit; like `no_text`, it remains sendable for `native_pdf` using the original PDF and blocks `pdf_text_extraction` until the user chooses native-PDF support or removes the file. A `no_text` PDF separately states that no extractable text was found and follows the same native-versus-extraction admission rule. The server independently enforces both blank-text cases. Newly introduced PDF warnings are announced once through the composer's existing feedback ownership and remain available by keyboard and touch without making every attachment chip a live region. Picker/drop acceptance uses that matrix, and switching models removes newly unsupported staged files with source-composer feedback instead of leaving an invalid send hidden in the draft. Each upload batch captures its source key and generation before awaiting; files settle independently so a failed item does not block later items, successes accumulate only at the source, and mixed-selection capability rejections compose with upload failures without being erased by a successful sibling or leaking into another chat/later batch.
- Staged attachments make every logical Search source whose current model would require query-only execution unavailable while retaining the user's saved selection; the direct picker and Run setup state only the attachment incompatibility and still allow deselection. A source that can run inside the selected answer connection remains selectable. The server independently resolves and rejects stale attachment-plus-client-Search requests, so browser state is never the privacy boundary.
- Send atomically snapshots and clears its source draft/attachments before the first await, while the store prevents a send and upload from starting over each other. Success or cancellation retires that snapshot; failure restores it only if the source has no newer draft/attachment revision, so sent attachments cannot leak into the next question and newer work always wins.
- Entering edit mode snapshots the source composer's unsent draft without touching staged attachments. Cancel restores that exact draft; successful edit retires it. Each keyed composer session owns at most one pending edit PATCH: repeated submit, Cancel, and edit replacement are disabled only for that source, while another chat may edit/send/run independently. Settlement remains fenced by source key, message id, revision, pending owner, and generation; success activates the canonical refreshed branch (or the decoded committed response if detail refresh is unavailable), failure leaves a retryable edit, and stale/cross-chat responses cannot clear newer input or scroll another chat.
- A committed user-message edit immediately starts the answer run for the new branch through the same run lifecycle executor as send/regenerate, keyed to the source chat even if the user navigated away. A rejected or ambiguous run start keeps the readable failed assistant tail on the committed branch instead of rolling the branch back to silence; the stranded-leaf reconcile before the next run mutation owns recovery. Assistant-message edits commit their replacement without a follow-up run.
- A failed assistant tail exposes one labeled `Retry answer` action beside its readable failure. It invokes the existing regenerate owner for that assistant and creates the normal sibling answer under the original user message; it does not delete, deduplicate, or rewrite the accepted failed turn.
- A blank root/folder session transfers atomically to the chat created by its first send. Creation or send failure restores the captured content under exactly one session when no newer work replaced it; a successful send retires only its pending snapshot and never clears a newer draft. If chat creation commits but the message request is rejected before acceptance, the chat remains selected as saved-empty with the bottom composer, restored draft, and `Send failed. Your draft was preserved.` feedback. Its rejected optimistic rows and unowned run surface are removed, so the centered blank stage and `Run error` chip cannot contradict the persisted chat.
- Deleting a folder removes its blank-folder composer session, discards late upload results, and returns an active blank-folder composer to blank root; saved chats moved out of that folder keep their own sessions.
- The attachment picker accepts multiple files in one selection, including PDF/image files plus `.txt`, `.md`, `.markdown`, `.csv`, `.json`, `.html`, and `.htm`.
- The catalog `documentInputMode` distinguishes `native_pdf`, `pdf_text_extraction`, and `none`; `imageInput` and `toolCalling` expose image and MCP-tool eligibility. The composer uses this backend-filtered model catalog instead of guessing from provider names.
- The composer input frame accepts dropped files from the same attachment set and passes them through the same upload path as the paperclip picker. File drags get a quiet proof-accent border/ring while over the frame. Non-file text drops are not intercepted. File drops while disabled, streaming, or already uploading are prevented from navigating away but do not start another upload.

## Command palette

- Ctrl/Cmd+K opens.
- Ctrl/Cmd+K is ignored while focus is inside text inputs, textareas, selects, or contenteditable regions.
- Escape closes.
- Arrow up/down wraps through results; Home/End moves to the first/last result.
- Enter executes selected item.
- Filtering covers actions, models, Search options, prompt presets, and the full workspace chat inventory, including provider/category aliases and non-presentational catalog ids in the model search index. A sidebar title/content query filters only workspace navigation and cannot remove chats from command-palette search.
- Results are grouped under readable Actions, Chats, Models, Prompts, and Search strategies headings with group counts. Current chat/model/prompt/search rows use a visible `Current` marker; category and readable provider/capability/search context form the secondary line instead of exposing raw ids.
- Long labels wrap, results scroll locally, keyboard movement keeps the active row visible, and an unmatched query replaces stale results with a readable `No matching commands` status. Enter does nothing when there is no result.
- The palette is viewport bounded. Arrow/Home/End/Enter operate its current option, and Escape or the backdrop closes it.
- Settings can be opened from the persistent Workspace Account footer, from the compact Workspace drawer, or from the command palette. Prompt library is a separate Account destination and opens contextually through `Open library` in composer Run setup.
- The command palette includes a `New chat` action for keyboard and mobile users.

## Left pane

- The header gives the proof-backed primary action to `New Chat`, keeps `New folder` secondary, and places one labeled search field immediately below them. `New Chat` remains the pane's first focusable action.
- Chat search filters lightweight loaded summaries locally by title/provider/model only. Loaded message bodies do not become an accidental second local-content index.
- Non-empty search text also debounces a `/api/chats?q=<query>` request and merges server-side message-content matches, so chats that have never been opened in the current session can appear. The pane distinguishes `Title match`, `Model match`, and `Message match`, announces result/message-match counts, waits before showing empty results, and reports message-search failure while leaving local title/model results usable.
- Search results retain matching ancestor folders and temporarily reveal matches under locally collapsed branches. Clearing search, including Escape from the focused search field, restores the user's stored collapse choices and scrolls the current chat back into view when available.
- Chats with no folder render as plain top-level rows without a synthetic folder header. `No folder` is the row-menu destination label and explanatory copy calls this the `top level`. Folder rows use bounded indentation for nesting, total visible descendant-chat counts, a project-memory cue, and an active-descendant cue; collapsing a folder hides its whole descendant branch without making the active location ambiguous.
- Chat titles may use two lines and always retain the complete value as a tooltip. Provider/model plus update-date metadata appears only for duplicate-looking titles, model-query matches, or chats whose saved model is no longer available for new runs. An unavailable chat keeps exactly one visible availability cue while remaining readable/switchable; archived chats are removed from the active workspace response and therefore do not render as disabled rows.
- Selected chats have one visible selected state; favorites use one quiet star cue; every in-flight chat id from `runLifecycleStore.activeStreams` gets a readable live indicator even while another chat is open. Favorites still sort before non-favorites, and each group stays newest-first within that split.
- Each chat reserves exactly one overflow affordance instead of a permanent delete/favorite icon toolbar. Its named popover contains Favorite, Rename, Move, Share, Export, and confirmation-gated Delete; folder popovers contain New chat, New subfolder, Project settings, Rename, Move, and confirmation-gated Delete. Popovers scroll locally, bring themselves into the navigation viewport, and close on Escape/outside click without activating the row beneath them.
- Chat and folder `Move to folder` controls use the shared finite-option picker rather than a native select. Destination rows show `Current`, preserve `No folder` / `Top level`, indent nested folders to a bounded depth while retaining the readable full path, support Arrow/Home/End/Enter, and scroll their result list locally. The picker expands inside the desktop popover and follows the shared viewport-bounded bottom-sheet contract below `sm`; choosing a different destination applies immediately, then the owning popover closes through the existing successful-move lifecycle.
- All confirmation flows use shell dialogs with Escape/backdrop cancel and appropriate destructive or warning styling; native browser `window.confirm`, `window.alert`, and `window.prompt` are not used for app confirmations. This includes chat, folder, message, and prompt deletion plus discard-unsaved-changes prompts.
- `New Chat` opens a blank workspace with no folder and without creating a persisted chat row. Folder-menu `New chat` opens a blank workspace with that pending folder, and persistence happens only on the first send.
- The compact edge-action `Start new chat` is another trigger for that same top-level blank-workspace action, not a second creation path; it preserves keyed drafts and does not stop an active run in the chat being left.
- Account provisioning creates no synthetic default folder. New chats stay at the top level unless the user explicitly starts or moves them inside a user-created folder; existing folders remain ordinary user-owned workspace data.
- The mobile workspace drawer button is the leftmost edge-action control and the compact route to Account, using the same left-pane icon language and leaving the pipeline and right-side Details controls separated.
- Folder creation hides behind a `New folder` header action that reveals an inline name input on demand; Enter creates, Escape cancels, and the input is not permanently visible.

The backend validates and commits the full preference with the accepted run without replacing it with the effective subset, so immediate reload does not depend on a separate in-flight settings autosave;

- current-user settings persistence has one shell-lifetime coordinator and at most one PATCH in flight. Pending scalar fields use latest-intent semantics, pending model drafts deep-coalesce by model key, and each decoded response reconciles only the fields its request touched before overlaying newer queued intent. HTTP/network/malformed-success failure keeps one recoverable pending patch behind a visible Retry action; a later settings intent also retries that retained work, while page-hide delivery remains best effort;
- model switches, chat activation, and page reloads restore that concrete model's reasoning/control draft while retaining the global preferred Search plan; compatibility changes only the derived effective subset;
- citation, reasoning-block, and tool-activity visibility toggles persist as current-user presentation defaults. Tool-activity visibility defaults on and hides only the inline disclosure; the durable calls and Details/Events evidence remain available and execution is unchanged;

## Run receipt

- Every non-streaming assistant answer can explicitly reveal one quiet compact evidence block through its own `More` → `Show run details`; hover, focus, and message tap reveal only the shared action dock and never mount the receipt. The block is derived only from that message's status, stored provider/model identity, bounded search/citation/artifact summary, message-bound warnings, and its message-bound persisted `runUsage` projection. Each completed answer therefore retains its own provider-reported normalized total after later runs and reloads; absent or zero usage produces no token fact. Search and citation facts expand their existing details inside that block instead of rendering as separate stacked summaries. It does not reconstruct historical Profile, Search, or other facts from the current composer/catalog defaults and adds no fetch, store, API, or inspection tab.
- Search, Tools, Citations, and Reasoning segments open the existing disclosure on their originating answer when that disclosure is rendered. A hidden evidence segment or status/model/usage/context/warning segment opens Details → Events only when the same answer owns the exact currently loaded persisted run and that run has real events. Otherwise the segment remains factual noninteractive text; a historical answer must never open another answer's Events. The receipt is absent while the answer streams.
- Hosted-answer native Gemini grounded output is a deliberate live-only exception. The current stream renders the answer only after a non-empty validated `grounding_display`, with safe transient citations and the exact Search Suggestions inside an isolated ShadowRoot. The component never sends provider markup through `MarkdownMessage`, an iframe, or ordinary `dangerouslySetInnerHTML` in the document tree. On navigation/reload the thread shows only the backend's neutral grounded placeholder/provenance; it does not reconstruct answer text, Suggestions, Links, or citation detail from current state. Query-only Gemini client Search never renders that markup and appears through the ordinary normalized Search disclosure.

## Details pane

- new sessions start closed; explicit Pin is the only open presentation persisted across reloads, and it restores only at the `>=1440px` eligibility breakpoint;
- run start/completion and fork activation never mutate Details presentation or steal focus;
- the full Details surface shows exactly Branch and Events, in that order;
- Details tabs implement one controlled roving tab stop with Arrow/Home/End navigation, visible focus, wraparound, and stable tab/panel relationships;
- the Details header shows readable active/error/run status and names the mode only when it is `Pinned beside chat`; the ordinary overlay needs no redundant subtitle, and errors are wrapped text rather than icon-only chips;
- Close removes Details; Overlay does not alter the grid; Pin adds the wide-only 360px column; Unpin keeps Details open as an overlay;
- the `Branch tree` item in `Conversation actions` opens Details on Branch at every viewport;
- readable live run activity opens Details on Events; no activity control is rendered while idle or settled;
- Run setup is the only UI editor for temperature and max-output drafts. Closing Details has no parameter-flush side effect because Details owns no drafts;
- overlay Details uses one shared responsive state and selector on desktop/mobile, with modal focus/background behavior only while overlaid;
- Details never presents next-run draft values as historical request inspection. Historical/deep request inspection stays in Events and model-run APIs; a future immutable Request tab requires a separate persisted data contract.
- More opens the Run setup that owns exact reasoning mode/effort, background, Stream, and the advanced inventory. Those controls appear only when the selected model's backend catalog advertises them; citations, reasoning display, tool-activity display, and answer sound remain user-facing preferences there.
- Events is a chronological digest with readable stage names, ordinal cues, semantic status glyphs, and plain-language detail. Provider/search/tool/citation/reasoning/token/usage noise is aggregated in place at each category's first occurrence, so later counts/details update without moving rows. Warning, long failure detail, cancellation, and successful completion remain distinct and fully wrapped; raw token deltas and internal assistant ids never render.
- empty Events states explain that events appear during a run and that a run never opens Details automatically;
- Branch renders readable Q/A role labels and plaintext multiline excerpts: stored Markdown remains unchanged, linear/current-path rows are static, depth increases only below actual fork points, only true alternate versions expose the user-facing `Open version` action, and the active leaf is named without exposing message ids;
- root-level siblings created by editing the first message are true forks: the version/message counts include them with correct singular/plural wording, exactly one leaf is `Current`, and the single-version explainer appears only for a genuinely linear conversation. Activating `Open version` checks out that branch's deepest leaf so the whole alternate conversation renders and the composer targets its leaf; checkout never auto-opens or closes Details;
- Branch empty/linear guidance explains that edit, regenerate, and Branch from here create branches;
- thread messages show one calm, direct, default-collapsed Search disclosure below an answer whenever hosted or client Search evidence exists, during execution and after reload. It is independent of `Show tool activity`; expansion gives friendly source/status/count facts, generated queries, safe normalized sources/citations, and bounded provider-reported search/open/find operations without technical routing. Historical/provider omission says detail is unavailable rather than showing zero, and failed/cancelled/partial execution stays explicit;
- when `Show tool activity` is on, each assistant run with observed non-Search client-executed calls shows a separate default-collapsed summary during execution and after reload. Expansion groups calls by model round, marks same-round batches as parallel, and gives each call a disclosure with MCP server/tool identity, live or terminal state, duration, safe account/credential-source metadata, and bounded redacted argument/result previews. Search capability calls are excluded from this generic summary so the direct Search disclosure is never duplicated. No raw executable configuration, endpoint, secret, opaque invocation id, or unrestricted payload is rendered;
- thread messages show optional collapsed citation disclosures when provider/search citation artifacts exist, including direct Perplexity answers and historical Perplexity search runs; links remain safe and long titles, URLs, and snippets stay contained;
- thread messages show a compact context-window hint before the answer when the backend emits a `context_truncated` artifact for dropped prior turns;
- Events shows context-window truncation as a warning row with dropped message/token estimates;
- empty citation/reasoning artifact disclosures state that no text was captured only after the user expands them;
- Branch checkout rows are disabled while a response is streaming and expose a visible stop/finish-first explanation.
- reasoning/thinking artifacts can be toggled visible from the composer control bar; provider summary arrays render as readable text blocks and empty fragments are not counted when text blocks exist.

# FRONTEND RUN CONTROLS

Owner: Chat interaction maintainers
Scope: Provider, model, Assistant, Search, prompt, and next-run control behavior and availability.
Read when: Changing provider/model/Assistant/Search selectors, parameter controls, next-run defaults, entitlement filtering, or unavailable-state behavior.
Code owners: Composer control cluster, catalog selectors, Search controls, run-parameter state, and Assistant selection.
Not owned here: Composer text/attachments, navigation, receipts/details, or server-side admission semantics.

## Provider/model/assistant/search controls

- options come from the backend-filtered current-user catalog;
- direct model, Search, and Knowledge pickers are present at every viewport, with **More** opening the complete Run setup. A combined current Reasoning mode/effort picker appears only when the composer's own controls container is at least 44rem wide and the viewport is taller than 42rem; narrower containers, enlarged text, and short-height composition keep Reasoning in More. Every presentation uses the same control actions and state owner;
- the direct Model action and the model editor in More open the same searchable grouped picker behavior; selecting a concrete model from another provider applies provider and model atomically;
- Assistant selection is opt-in and secondary: the Assistants surface, Command palette, and Run setup's `Use an assistant…` action open the searchable quick picker with Pinned, browser-local Recent, Yours, and Shared groups plus `Create from current setup`, `Manage assistants`, and — only while selected — `Remove assistant`. Rows show avatar, name, a compact capability summary, and an explicit privacy-neutral unavailable state without technical ids. Only a selected Assistant renders the compact avatar-and-name chip adjacent to the controls; the ordinary composer stays unnamed with no placeholder, `Custom`, or `Default` label;
- the Assistant quick picker remains a modal with a scrim, contained focus, initial Search focus, Escape/backdrop dismissal, and a visible explicit Close action routed through the same close owner. Its compact and short-height sheet clears the applicable top/left/right safe areas, keeps actions above the bottom safe area, and gives Close a coarse/no-hover touch target. Search and Knowledge pickers remain non-modal disclosures with document outside-pointer dismissal and no scrim, inert background, or `aria-modal`; their compact and short-height sheets clear every safe-area edge, keep one local scroller, and use the same coarse/no-hover Close geometry without enlarging the desktop control;
- selecting an Assistant applies its currently authorized revision atomically to the existing control owner while keeping the underlying Model/Search/Knowledge/More controls visible for transparency. Its ordered Knowledge base list is exact and is never merged with chat or project defaults. Strict identity: any manual change to an Assistant-governed control (model, Search, Knowledge, reasoning, temperature, output limit, background, Stream) removes the Assistant identity, keeps the resolved values plus the change as the ordinary unnamed draft, discards the preserved backup, and shows one dismissible non-blocking `Assistant removed` note. Explicit `Remove assistant` instead restores the preserved ordinary manual draft. A selected Assistant auto-follows its currently authorized revision at send; the server records the exact revision used and no stale-revision dialog exists. Assistant-derived values never overwrite the user's saved defaults or per-model drafts, and an Assistant send carries only the Assistant identity plus user content — never an expanded client copy of the governed controls;
- when an Assistant is selected and the blank state is eligible (no messages, empty draft, no staged attachments or uploads), the thread renders the identity intro — avatar, name, description — above the composer with at most four ordered starter prompts. A starter click sends its stored prompt as an ordinary user message through the exact normal send/admission path and never pre-fills the composer; starters hide as soon as the draft, attachments, or any real message exists. The intro is UI chrome, never a stored message or branch node;
- model picker provider group headers are noninteractive headings with model counts; each concrete row has one focusable selection control plus, when it is not already personal, a compact independent `Make default` action. Selecting applies its provider atomically, while the default action never changes the current next-run selection;
- provider connection labels resolve once from the filtered catalog and remain shared by the picker groups/actions, current/default summaries, Command palette, workspace/thread metadata, titles, and accessible names. A normalized case/whitespace collision adds a deterministic short opaque connection reference to every colliding display name; a unique name stays unchanged. The reference derives only from the already exposed exact connection identity, never replaces that binding, and never renders the raw full id, credential/account label, endpoint, organization metadata, or secret;
- Search is a direct labeled multiselect over the user's complete entitled logical source set. Each exact provider connection appears once with a friendly source name; hosted/query-only route, revision, adapter, and technical model are absent from ordinary UI. Its resting state is `Search: Off`, the one selected source name, `Search: N engines`, or `N active · M unavailable`; the accessible description/title and complete Run setup retain ordered names plus `All selected per search` or `Model chooses`. The picker preserves and allows removal of sources incompatible with the current model, disables incompatible additions, and offers `Use organization default` for a personal preference. It never silently substitutes or deletes a source during a model change;
- Knowledge is a direct ordered multiselect of at most three authorized bases. Its resting label is Off, one base name, the selected count, or the split active/unavailable count; its accessible name retains the complete ordered plan and source (`Assistant`, chat default, project default, or explicit next-run plan). Missing and archived selections remain visible and removable but cannot be newly added. Ordinary precedence is explicit next-run plan, then chat default, then project default, then Off; an explicit empty plan means Off. The picker can save or clear the active chat default, while Project settings owns the project default. Changing the plan manually while an Assistant is selected produces one explicit ordinary plan and removes Assistant identity;
- Run setup is a modal bottom sheet on narrow screens and a centered viewport-bounded modal on wider screens, with a scrim, explicit Close, safe-area padding, and one locally scrolling content owner. Its valid computed maximum block size subtracts the desktop gutter plus safe-area insets before centering, so a naturally tall form never extends below the viewport. Model, Reasoning, Search, and Knowledge precede the complete advanced inventory. At the desktop dialog width, labels remain readable without making any plan inaccessible. Nested pickers close back to Run setup without resetting it. Closing Run setup flushes numeric drafts and returns focus/state to the direct controls; Ctrl/Cmd+K stays blocked while the modal owns the layer;
- the shared advanced inventory contains the `Use an assistant…` action, temperature, max output tokens, model-specific reasoning mode, background mode, provider Stream response, citation visibility, reasoning display, tool-activity display, and answer sound. Mode appears only when the backend catalog advertises it, and unsupported capabilities stay disabled or absent;
- response/display/sound switches use full readable labels with On/Off state; an in-flight answer reads the latest answer-sound preference when it actually completes, so changing the switch during a run affects that run's terminal notification;
- provider/model/Search changes affect the next message only. Search intent and per-model control drafts autosave through current-user settings, but ordinary model selection—including Command palette selection—never changes a personal or installation model default. Assistant selection is browser-session state and persists nothing;
- the model picker marks `Current`, `My default`, and the safely entitled `Organization default` independently. Each non-personal row's `Make default` writes that row's exact deployment explicitly without selecting it first; `Use organization default` clears the personal override through the serialized settings coordinator. A null personal default inherits dynamically. An unavailable non-null personal default projects as absent and suppresses organization fallback, while an unavailable organization default also projects as absent; neither hidden deployment identity nor a first-visible substitute is exposed;
- users with no entitled catalog models see a disabled `No models available` composer control and a model-access hint, not a saved/default provider-model pair;
- Search-plan changes save one global personal preferred plan; explicit Off is an empty personal plan, while `Use organization default` restores nullable inheritance. Model selection only derives the compatible effective subset used by the next run and never persists Search. Retained incompatible engines are visibly unavailable and become active again when the model supports them;
- per-model run-control drafts save background mode, Stream mode, exact supported reasoning effort/mode, temperature, and max output tokens. Unsupported stale values clamp to that concrete model's catalog defaults without cross-provider mapping. Old per-model Search singleton hints are migration input only;
- send and regenerate payloads include the current per-model `controlDefaults`, the model-compatible effective `searchPlan`, and separate preferred-plan/source intent. The backend validates and commits the full preference with the accepted run without replacing it with the effective subset, so immediate reload does not depend on a separate in-flight settings autosave;
- attachment-only sends use structured optimistic user-message content so staged image/file/PDF/text document chips are visible immediately instead of waiting for a canonical chat update;
- typed temperature and max-token changes are debounced before saving, with blur, Enter, Run setup close, or shell unmount flushing the pending save; same-model immediate background/Stream/reasoning toggles merge and clear pending numeric drafts so late debounce flushes cannot clobber newer toggles;
- current-user settings persistence has one shell-lifetime coordinator and at most one PATCH in flight. Pending scalar fields use latest-intent semantics, pending model drafts deep-coalesce by model key, and each decoded response reconciles only the fields its request touched before overlaying newer queued intent. HTTP/network/malformed-success failure keeps one recoverable pending patch behind a visible Retry action; a later settings intent also retries that retained work, while page-hide delivery remains best effort;
- model switches, chat activation, and page reloads restore that concrete model's reasoning/control draft while retaining the global preferred Search plan; compatibility changes only the derived effective subset;
- citation, reasoning-block, and tool-activity visibility toggles persist as current-user presentation defaults. Tool-activity visibility defaults on and hides only the inline disclosure; the durable calls and Details/Events evidence remain available and execution is unchanged;
- OpenAI, Gemini, and OpenRouter expose the Stream response setting when the current model's catalog controls support user selection; OpenAI defaults off, Gemini/OpenRouter default on, and providers without Stream-control support can still stream through their adapter defaults.
- model selection is searchable and grouped by provider;
- model search matches provider display name/family, model display name/upstream id, and readable capability text without rendering internal connection or deployment ids. Provider sections remain visible as noninteractive headings with model counts and optional current-group context;
- the model picker clears its search query after a model selection, closes if another surface such as Command palette changes the selected model while it is open, and renders a dedicated zero-match status instead of an empty or stale list;
- model rows wrap long display names and use readable capability text such as `Reasoning`, `PDF and documents`, `Web search`, and `Streaming`, never internal ids or a row of tiny uppercase chips. Capabilities that distinguish a model inside its provider group appear first with normal emphasis while shared capabilities remain readable but quieter; the complete inventory is retained. Command-palette results use the same plain vocabulary while technical ids and aliases remain search-only; current selection and default facts remain independent;
- Search sources and other finite pickers share the same readable row recipe: label, meaningful source description, selected state, bounded local scrolling, and a dedicated unavailable-options state. Search opens directly from the composer and remains editable in Run setup without gaining a redundant query field; Run setup discloses the complete logical plan, readiness/compatibility facts, and orchestration mode, but never physical route choices;
- model, search-strategy, and finite-option picker rows support pointer selection plus Arrow up/down, Home/End, and Enter navigation. Escape and outside click close the session;
- picker surfaces have purposeful desktop widths and local maximum heights. On narrow or short-height screens they become safe-area-aware bottom sheets with contained scrolling, wrapping labels, and capability-driven touch-sized rows instead of clipping outside the viewport;
- internal provider/model ids never appear in ordinary UI; the collision-only opaque connection reference above is presentation identity, not a raw id. Upstream API ids remain available only where they carry configuration or diagnostic meaning, such as the OpenRouter discovery picker, compatible-provider fields, Advanced model settings, and deep API inspection; routine model rows, answer metadata, chat metadata, grants, usage, and unavailable fallbacks use display names or neutral copy;
- model display names do not repeat the selected provider in suffixes such as `via OpenRouter`; the compact composer trigger shows the provider and model as separate readable facts, while the expanded picker groups models under visible provider headings;
- Escape and outside click close picker/popover and left-pane action-menu sessions where safe.

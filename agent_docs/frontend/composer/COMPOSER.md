# FRONTEND COMPOSER

Owner: Chat interaction maintainers
Scope: Functional composer input, attachment, draft, submit, keyboard, validation, and responsive interaction contracts.
Read when: Changing the Chat composer, input lifecycle, attachments, drafts, submit behavior, shortcuts, validation, or mobile interaction.
Code owners: Composer components, Chat draft state, attachment controls, and submit handlers.
Not owned here: Visual recipes, workspace navigation, next-run selectors, answer outputs, or Branches.

## Composer

- Enter sends.
- Enter does not send while an IME composition is active. One client-safe guard recognizes native/React composing state, `Process`, and legacy keyCode 229 across the composer, command palette, shared pickers, and inline chat/folder create/rename handlers; composed Enter/Escape never commits or cancels partial text.
- Shift+Enter inserts newline.
- The visible `Send` action keeps the stable label `Send`. It is disabled while streaming, while a blank workspace is creating its first persisted chat, or while empty with no staged attachments. In edit-branch mode, attachments alone are not sendable: edited text is required, and `Cancel edit` remains available in the branch strip.
- Composer input stays disabled until catalog and workspace/chat-detail bootstrap complete and whenever the current user has no entitled model. Loading, no-model, creation, and actionable disabled reasons render as status text in the composer frame.
- Send is disabled while uploads are in flight so a message cannot silently skip a staged file. The textarea remains draftable, the frame reports `Uploading…` as status/busy feedback, and file selection/drop is unavailable until the upload settles.
- The visible `Stop` action remains available while the active chat streams. It stays disabled with `Starting run…` until the client has the persisted model-run id needed to call the server cancel endpoint. Stop requests durable cancellation before aborting the browser stream or painting a cancelled tail; a losing cancel reconciles the returned current status instead of fabricating local cancellation.
- When another chat's response is still running, the current chat's composer can draft and send its own run; only the chat that already has an active stream is blocked from sending another run.
- Switching away from and back to a chat with an in-flight foreground stream preserves optimistic user/assistant rows and cached token deltas until the final `chat_update` canonicalizes the thread.
- Draft text, staged attachments, edit intent, pending send/upload generations, and operation feedback belong to one keyed in-memory composer session: a saved chat, or a Normal/Temporary variant of the blank root or a specific blank folder. Navigation only selects that key; it does not copy composer content through a singular active buffer. Blank Normal and Temporary variants never share drafts or staged state.
- Reload/background-run resume polling distinguishes a found run, proven 404/not-found, and transiently unknown network/non-2xx/malformed reads. Unknown reads retain only that source chat's run gate and continue bounded backoff; at the horizon the gate remains until `Check run`, cancellation, navigation-owned exit, or a later proven terminal read, while other chats remain sendable.
- A refetched model-run outcome is always written to its explicit source chat key, including after navigation. The active-chat selector alone chooses what is rendered, so a slow run GET cannot paint stale status, errors, citations, or outputs into another chat. The read exists for recovery and terminal reconciliation, not post-hoc inspection.
- Textarea auto-grows to 200px max.
- The Reading Room composer keeps ring 0 to Message, one `+` capability action, the current model, compact active-capability indicators, and Send/Stop. `+` is the single predictable entry for Assistant selection, Attach, Search, up to three Knowledge bases, MCP servers, and model parameters; no advanced run control is more than two actions away. Desktop disclosures are bounded local popovers, while narrow or at-most-32rem-high viewports use one safe-area-aware bottom sheet with a local scroller and coarse Close target. Loading, malformed bootstrap, and no-entitled-model states keep Message and Send disabled with a visible neutral reason; no stale active indicator is painted without a decoded configuration.
- The whole composer is centered and capped at the reading measure. Edit/disabled strips, attachments, textarea, controls, context/usage, and actions stay inside the same frame rather than stretching independently across the conversation.
- A ready blank workspace centers that same composer and its short orientation copy in the conversation stage. As soon as first-chat creation begins, a saved chat owns the session, or any optimistic/persisted message exists, the composer moves to the docked thread tail; there is never a second composer or draft owner. A selected Assistant may replace the generic orientation with its avatar, description, and up to four starter prompts without creating stored messages.
- The draft has one bounded Message plane at every viewport. Its `Message` label remains available to assistive technology while `Ask anything…` is the visible resting cue. It never collapses to an alternate compact composer; responsive changes preserve the same textarea, controls, draft, and Stop owner.
- The control row contains `+`, one readable provider/model picker, compact indicators only for selected Search/Knowledge and enabled MCP, the context gauge when estimates exist, and Send/addressable Stop. The model picker is searchable and grouped by provider. `+` exposes the complete capability inventory and model-parameter entry in one locally scrolling surface; it does not create permanent Search/Tools rows. MCP readiness refresh preserves last useful state until a successful replacement. The gauge uses the safe input budget—not total context—as its denominator and opens the single disclosure for approximate input, safe budget, total context, active-branch messages, and matching provider-reported usage.
- Draft text, attachments/uploads, edit work, actionable errors/unavailable states, and streaming cancellation all render within that same composer. Stop remains visible while streaming and stays disabled with `Starting run…` until the persisted run id exists.
- Attachment rows support uploaded PDFs, images, text/HTML/JSON/CSV/Markdown, DOCX, XLSX, PPTX, DOC, RTF, and ODT. Every new file renders its truthful `Processing…`, `Ready`, or bounded failure state adjacent to the filename; a failed row normally offers labeled Retry and Remove actions. A status `404` becomes an unavailable failed row with Remove only because the deleted attachment cannot be retried. Reaching the 15-minute client poll horizon becomes a failed row whose Retry resumes status polling instead of requesting a server requeue while the durable attachment may still be processing. Draft text remains editable while processing, but keyboard/button/programmatic send is blocked until every staged row is ready. Polling captures the source composer key and updates only a still-present matching attachment, so navigation cannot paint another chat. Text documents remain available to every selected catalog model because ready rows become extracted provider text; PDF availability follows `documentInputMode`, and images follow `imageInput`. A PDF whose bounded extraction is `partial` with retained text stays sendable and shows per-file caution that only the available text will be used. The valid zero-emitted `partial` edge states that no complete PDF text fit within the configured limit; like `no_text`, it remains sendable for `native_pdf` using the original PDF and blocks `pdf_text_extraction` until the user chooses native-PDF support or removes the file. The server independently enforces both blank-text cases. PDF warnings are announced once through existing feedback ownership and remain keyboard/touch accessible without making every chip a live region. Picker/drop acceptance uses that matrix, and switching models removes newly unsupported staged files with source-composer feedback. Each upload batch captures its source key and generation before awaiting; files settle independently, successes accumulate only at the source, and mixed-selection rejections compose with failures without leaking into another chat/later batch. Above staged files, one compact capacity summary reports unique count and known source bytes, cautions at the inclusive 80% boundary, and blocks ordinary sends only after the catalog-projected count, materialized-binary, or encoded-provider limit is exceeded. The binary estimate follows the selected model; unavailable catalog/model data uses conservative defaults. Picker/drop batches that would exceed count are rejected before upload. Safe server failures stay attached to the restored composer, and removing a file clears only that limit feedback.
- Staged attachments never disable, filter, or rewrite Search choices. Send and regenerate retain the same selected effective plan whether Search executes inside the answer-provider request or through a query-only client route; the server-owned query-only boundary still prevents attachment ids, names, bytes, or extracted text from entering a client Search request.
- Send atomically snapshots and clears its source draft/attachments before the first await, while the store prevents a send and upload from starting over each other. Success or cancellation retires that snapshot; failure restores it only if the source has no newer draft/attachment revision, so sent attachments cannot leak into the next question and newer work always wins.
- Entering edit mode snapshots the source composer's unsent draft without touching staged attachments. Cancel restores that exact draft; successful edit retires it. Each keyed composer session owns at most one pending edit PATCH: repeated submit, Cancel, and edit replacement are disabled only for that source, while another chat may edit/send/run independently. Settlement remains fenced by source key, message id, revision, pending owner, and generation; success activates the canonical refreshed branch (or the decoded committed response if detail refresh is unavailable), failure leaves a retryable edit, and stale/cross-chat responses cannot clear newer input or scroll another chat.
- A committed user-message edit immediately starts the answer run for the new branch through the same run lifecycle executor as send/regenerate, keyed to the source chat even if the user navigated away. A rejected or ambiguous run start keeps the readable failed assistant tail on the committed branch instead of rolling the branch back to silence; the stranded-leaf reconcile before the next run mutation owns recovery. Assistant-message edits commit their replacement without a follow-up run.
- A failed assistant tail exposes one labeled `Retry answer` action beside its readable failure. It invokes the existing regenerate owner for that assistant and creates the normal sibling answer under the original user message; it does not delete, deduplicate, or rewrite the accepted failed turn.
- A blank root/folder session transfers atomically to the chat created by its first send. Creation or send failure restores the captured content under exactly one session when no newer work replaced it; a successful send retires only its pending snapshot and never clears a newer draft. If chat creation commits but the message request is rejected before acceptance, the chat remains selected as saved-empty with the bottom composer, restored draft, and `Send failed. Your draft was preserved.` feedback. Its rejected optimistic rows and unowned run surface are removed, so the centered blank stage and `Run error` chip cannot contradict the persisted chat.
- When the settings capability advertises proven Temporary deletion, a blank session chooses Normal or Temporary through the sidebar New-chat mode menu; the composer renders no permanent memory indicator in either mode. Cancel Temporary is available only before first send by returning to the paired Normal blank session, which keeps its own separate unsent draft. The choice locks as soon as first send begins and remains immutable; ambiguous retries retain the reviewed intent. Only the Temporary first message sends the strict `chatMode: "TEMPORARY"` and `temporaryRetentionPolicyVersion: "temporary-24h-v1"` pair, while later runs omit both admission fields. The client reconciles the authoritative mode and deadline from the private chat lifecycle read, shows one quiet Temporary indicator in the workspace header — its click disclosure repeats the exact localized retention, deadline, and external-destination copy — and exposes neither Share nor an active-navigation row for that chat.
- Deleting a folder removes its blank-folder composer session, discards late upload results, and returns an active blank-folder composer to blank root; saved chats moved out of that folder keep their own sessions.
- The attachment picker accepts multiple files in one selection, including PDF/image files plus `.txt`, `.md`, `.markdown`, `.csv`, `.json`, `.html`, `.htm`, `.docx`, `.xlsx`, `.pptx`, `.doc`, `.rtf`, and `.odt`.
- The catalog `documentInputMode` distinguishes `native_pdf`, `pdf_text_extraction`, and `none`; `imageInput` and `toolCalling` expose image and MCP-tool eligibility. The composer uses this backend-filtered model catalog instead of guessing from provider names.
- The composer input frame accepts dropped files and clipboard file items from the same attachment set; picker, multi-select, drop, and paste all pass through one capability partition and upload owner. Ordinary text paste and non-file text drops are not intercepted. File drags get a quiet proof-accent border/ring while over the frame. File drops or pasted files while disabled, streaming, or already uploading do not start another upload; drops are still prevented from navigating away. The staged-file surface always distinguishes Uploading, Processing, Ready, unsupported format, too large, and processing failure with exact Retry/Remove resolution, while the `+` menu and attachment tray repeat the private-to-owner disclosure.

# FRONTEND MESSAGES AND MARKDOWN

Owner: Conversation-content UI maintainers
Scope: Functional message, branch, citation, generated-output, disclosure, safe Markdown, code, math, and overflow interaction contracts.

## Messages

- private user/assistant articles are named `Question`/`Answer`; repeated turn actions reference a short target description so their destination remains unambiguous;
- user and assistant edits fork same-role branch replacements without mutating descendants;
- the edit strip states that sending creates a new branch;
- sending an edited user message streams a fresh answer on the committed branch; an edited question never remains a dangling branch without an answer, an active run, or a readable run error;
- failed edit branch mutations keep source-keyed feedback and preserve that session's draft/editing state; one pending edit owner suppresses duplicate PATCHes without disabling another chat;
- Regenerate is the first action for either role: on an answer it forks a sibling assistant run, while on a question it starts the same assistant-sibling branch directly from that user message;
- regenerate is disabled while a response is streaming;
- settled message actions are contextual. Fine-pointer hover, keyboard focus, or an explicit compact/coarse tap reveals the exact turn's Regenerate/Edit/Copy/More toolbar without making blank gutters interactive; the newest settled answer keeps its toolbar visible without hover so the last answer stays one action away. An answer whose run has not settled renders no toolbar at all. Enter/Space toggles the toolbar for a keyboard-focused turn and Escape closes it. More contains only destructive/branch actions, is portalled above clipping owners, chooses an in-viewport placement, supports Arrow/Home/End navigation, and restores focus to its trigger; Delete inside it always routes through the shell confirmation dialog;
- a valid explicit Send in the still-active chat moves that thread to its optimistic newest user turn exactly once. A newest question that fits the thread viewport retains bounded preceding context; when that question is taller than the viewport, its trailing edge and the beginning/status of the new answer share the viewport instead. Later answer growth preserves either user-turn reading anchor rather than following the tail, while source-mismatched/background work cannot scroll the selected chat;
- send/regenerate optimistic rows, ids, tokens, and status patch only the source chat's keyed thread snapshot, including while another chat is visible; transient terminal `chat_update` patches that snapshot plus its compact navigation summary through separate projections. A pre-accept HTTP rejection removes only its owned temporary rows and restores the previous leaf; for a first send whose chat row already committed, it also clears the rejected lifecycle state while retaining that selected saved-empty chat and its restored composer feedback. Accepted network/SSE loss without a terminal frame keeps the partial answer and a source-keyed `Connection lost · Refresh` state; only that explicit Refresh force-refreshes the source, while retry refuses to post from a stranded temporary id until reconciliation succeeds. Complete is shown only from an authoritative terminal server transition. One stable shell-owned live region announces meaningful current-run activity changes and the terminal complete/error/stopped outcome with composer readiness; historical terminal state is not re-announced on activation. Lazy detail fetches are otherwise reserved for uncached/incomplete activation, recovery, export, and fallback paths;
- the one-line run activity maps only normalized lifecycle facts such as queued, preparing, searching, calling a tool, generating, and finalizing. Elapsed time, answer prose, and missing updates never manufacture a phase or percentage. While a run is live its answer shows only this status line and streamed text—no settled-output row and no action toolbar. Raw run/request identifiers remain internal. Send becomes Stop while a source run is active, but Stop stays unavailable until the server supplies the durable run id and cancellation reconciles that exact source;
- ordinary chat opening renders only the newest server-bounded active-branch page. When more history exists, one keyboard-reachable `Load earlier messages` control prepends the next page, owns local loading/error/Retry state, and preserves the first previously visible message instead of moving the composer or forcing Latest. The first loaded row may truthfully retain an off-page parent until its predecessor page arrives;
- Branches checkout changes the same chat's active leaf and future sends continue from that selected branch. Selecting an unloaded version persists the leaf and then replaces the thread with that branch's bounded tail instead of deriving it from absent messages. Pending checkout writes serialize per chat; Send waits for the selected leaf to settle, carries that exact nullable leaf to the server, and restores its draft without issuing a second checkout or run request when settlement fails or is superseded;
- a message with same-role siblings renders a compact `N/M` previous/next pager beside that exact turn, kept visible without hover or the Branches drawer. Each arrow resolves to the selected sibling's settled leaf, never to an inferred visible-cache descendant; unavailable directions and all checkout while the source run is streaming are disabled with readable guidance. The bounded-plaintext compact DAG projection backing the pager and Branches loads lazily per saved chat revision once that chat has committed messages, defers background refresh while its stream is live, and stays outside the rich thread cache;
- the Branches drawer is an explicitly opened temporary overlay, not a persistent conversation column or automatic response to branch creation. It traps focus, makes the rest of the workspace inert, restores the invoking control on close, and presents bounded previews as numbered original/edit/regenerate versions without raw ids. Loading, empty, graph-load failure, checkout-pending, checkout-failure, and streaming-disabled states remain in the drawer; a failed checkout leaves both the drawer and current version in place;
- deleting a message asks through a shell confirmation dialog, then removes that message and its descendants so the message DAG remains valid;
- archiving a chat from its navigation row moves it to Archived chats, updates the compact list, and selects another chat or the blank workspace; permanent deletion is reachable through the capability-gated `Delete…` entries and always passes through the existing confirm surface with unchanged gating and semantics;
- deleting a chat removes it with a functional chat-list update so concurrent stream/list patches are preserved;
- `Branch from here` clones the selected message's visible ancestor path into a new chat;
- `Copy message` copies only the selected visible message text;
- `Copy thread` and chat export always cover the complete active branch. Export defaults to a readable Markdown document and JSON remains the second option. If the rendered cache holds only a tail, these operations load remaining fenced pages into operation-local memory with readable preparing/failure feedback and never publish those pages into the rendered thread or produce a partial result labelled complete;
- assistant answers carry no permanent provider/run metadata line. A frozen Assistant identity may render only when the accepted-answer contract supplies it; absent identity remains absent rather than falling back to adapter/provider ids, raw model ids, or UUIDs. Model bindings, accepted parameters, request/response previews, internal events, retrieval internals, tool traces, and per-answer token breakdowns do not render in ordinary Chat;
- the optional collapsed Reasoning disclosure renders persisted provider-supplied reasoning through the same safe Markdown pipeline instead of literal markup. Its header is plain `Reasoning`; the UI does not infer or display an execution duration from internal events;
- a question sent with attachments keeps one quiet owner-only line of exactly the attachment labels the thread snapshot already exposes; storage keys, URLs, and attachment ids never render there;
- user questions and assistant answers share the composer's `max-w-reading` alignment; questions stay narrower/right-aligned while answers use the full readable document measure;
- completed assistant answers leave extra bottom scroll space so the final answer can sit comfortably above the composer; cancelled and failed tails keep a smaller terminal spacer;
- provider labels in workspace rows use the same catalog-resolved connection display label shown before send, including its collision-only opaque short reference when necessary, instead of raw provider ids; thread answers render no provider label at all;
- main thread and branch labels do not display raw message UUIDs;
- branch controls change active leaf and the thread renders the active branch path;
- provider/search/malformed-frame warnings remain bound to their originating answer through internal ids and render only beside that answer, so branch checkout cannot move them to unrelated content;
- completed hosted or client Search may expose one simple default-collapsed `Sources` disclosure below its answer when at least one safe source exists. It lists normalized source title/domain/link data and may merge near-duplicate safe URLs with a visible count. It does not expose attempt ordinals, generated queries, provider operations, route/revision facts, Knowledge scores, thresholds, candidate counts, or generic `Used tools` history. When no safe source exists, no Sources placeholder renders;
- a tool requiring approval presents that approval before execution. A concise result confirmation may render after an explicitly approved external effect or Memory Save/Update/Forget commits; post-hoc arguments, results, schemas, endpoints, and internal call history do not render;
- `Share (anonymously)` opens the Share dialog for the visible branch instead of publishing directly. The dialog explains that creating a link publishes a read-only sanitized snapshot, lists the chat's live links with per-link revocation, and mints a link only through the explicit create action. Share busy state affects only share controls, never composer/send/streams. The public viewer is dynamic and no-store with noindex/nofollow/nocache metadata; crawler hints do not replace bearer-link secrecy, revoke, or expiry.

## Generated Artifacts

- a generated file is a versioned result bound to the exact historical assistant message and branch that produced it; replacing or regenerating an answer creates another immutable version instead of changing a prior card;
- each ready card identifies its safe type, filename, version, size, and available Preview, Download, and `Use in next message` actions. Several files retain their server order as separate cards;
- lifecycle text reflects only normalized detected, validation, preview-rendering, ready, failed, or cancelled state. A validation failure keeps one bounded reason and Retry; a failed or unavailable preview never disables an independently valid download;
- the preview drawer traps focus, restores its opener, contains its own table/page overflow, and lists lineage through safe version and source-message labels without exposing internal ids, storage keys, or durable object URLs;
- generated-file presentation remains fixture-only until its authenticated backend contract is released. The fixture route is available only in explicit non-production test mode; ordinary product runs and production builds cannot manufacture file results.

## Markdown

- inline `\\(...\\)` / conservative `$...$` and display `\\[...\\]` / `$$...$$` formulas render lazily through the restricted local KaTeX boundary; incomplete, malformed, unsupported, or refused TeX remains readable escaped source, and inline/fenced code never becomes a math delimiter;
- fenced code blocks render with a header row, readable language label, and compact copy-code button;
- completed code blocks for `ts`, `tsx`, `js`, `json`, `bash`/`shell`, `python`, `go`, `rust`, `sql`, `yaml`, `html`, `css`, `md`, and `diff` highlight through one lazy Shiki singleton that emits `github-dark` and `github-light` token values as CSS variables inside the local semantic code container;
- unknown or absent fence languages render as plaintext with no raw info-string label;
- streaming assistant messages keep code blocks plaintext and do not start Shiki work until the message completes; highlight results are cached by language and code text;
- public share pages use the same `MarkdownMessage`, so highlighting and copy-code behavior have no auth-only assumptions;
- answer heading levels are offset by one (`#` starts at `<h2>`) so embedded Markdown never competes with the shell/public-page `<h1>`;
- paragraphs, headings, inline code, links, citation text, and artifact previews contain unbroken strings; tables, display math, and fenced code own named, focus-visible local horizontal-scroll regions that respond to native keyboard scrolling and never widen the shell;
- blockquotes separated by a blank unquoted line render as distinct blockquotes;
- unsafe links and raw HTML remain inert.

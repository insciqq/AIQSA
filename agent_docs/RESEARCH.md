# Research

Deep research is a run of the agent, so [Run contracts](RUN_CONTRACTS.md) applies to it first; this document holds only what is particular to research.

Operator decisions 2026-11-01. Only the user starts it, by choosing Deep research in the `+` menu for one message (operator decision 2026-11-05, replacing the model's choice from the user's words: a short question after a finished research started a second hour-long run). The choice is frozen with the run's bindings; no words in a chat start research. A message sent with it is never regenerated (operator decision 2026-11-06, replacing the 2026-11-05 regenerate that kept the choice): one click reran a half-hour research, so its answer offers no Regenerate, Retry or another model, the server refuses the call with a stable code for a tab opened earlier (`DEEP_RESEARCH_REGENERATE_REFUSAL`), and an edit of the message starts a new research on purpose. Its tools and prompt section ride only on that run, an approval continuation of its research and a Continue of an interrupted one, and only the server's bindings authorize those two: a turn they continue must have been admitted with the choice, and each Continue on the way must have gone on from an interrupted run, since the word may follow a finished answer. A start call in the items proves only that research started: a model may write one where research was not offered, and an interruption may cut off its refusal. That run's first step is certainly `start_research`: no other call runs before the start passes, even beside it, and a turn ending without it fails visibly. A message where research cannot run is refused at admission with a stable code (`deepResearchRefusal`). Narrowing admission must leave a visible way forward, so the ordinary prompt has one constant line naming the control. Accepted cost: a research turn's tools and prompt differ from an ordinary turn's, one cache miss at the start of a long run. Research stays in one run that ends in an ordinary answer: Stop ends it, so researchers run in the foreground, and a restart never replays it. The server holds the report back until its gates end; a failed gate or the deadline leaves a visible note, never a lost answer (`lib/server/research/run.ts`).

The research system rests on one contract (`lib/contracts/research.ts`, which holds every number below) and one set of ports (`lib/server/research/ports.ts`). These decisions bind each part:

- No clarifying questions. The user may give the request and leave, so what the model lacks becomes a named assumption, or a branch when it changes the result.
- The user may not know what matters for what they ask about, so the model scopes first: it reads how such a thing is chosen and finds the criteria itself, and the user is told plainly that a plan is being made. Scoping's limit is the server's: past it only the plan's call still runs, and a model that never proposes still ends in an answer, marked as unchecked.
- The plan window, as in ChatGPT Deep Research: a short plan the user can change for a moment. With no action, research starts. The start button, a saved edit and a chat message end the window at once, an edit in progress holds it through a lease, and an abandoned edit releases the last saved plan. A closed tab changes nothing. The window's times are the server's, so a countdown survives a reload and a wrong client clock. A person edits the plan's words, never its questions, so a changed plan holds researchers back until the model has rebuilt the questions from those words (decision 2026-11-01).
- Time: phases count from the plan's release, and research winds down through them to a hard end, never a silent crash or an unmarked incomplete answer. Only a research run's turn is extended, once, at that moment. One researcher's turn has its own limit, so one stuck agent cannot spend the budget, and time ending a researcher is a result the main agent goes on from, never a failure. The main agent's tools close when running researchers stop, so it hands in a report; the checks keep theirs for as long as their phase needs. The hard end moves the turn's end either way, so a longer configured turn gets the same 90 minutes. A VM's own idle stop is fixed before anyone knows a run will research, so every VM's allows for it (accepted: after an app crash a guest may stay up longer). Stop works in every phase.
- An approval continuation is a new run of the same research: it works on the rows of the run that started it, named by that start call's stored result, which counts only when it names a run of the branch. Its phases start afresh, so a long wait for a person is not charged to research.
- Research never waits for a person to pass a CAPTCHA or sign in (decision 2026-11-02, replacing the shorter handoff of 2026-11-01): it runs for half an hour or more and the user may have left. It passes a check itself as a person would, in bounded tries (operator decision 2026-11-20).
- How a site closes (operator decision 2026-11-05, replacing "at once" of 2026-11-02): the browser comes first. An agent with the Workspace browser records a site unreachable only once its own commands show the browser at work on that host, a step line in their output or a navigation they name, read from its call rows and never from its word; one without the browser, its tool groups included, records it at once. Accepted risk: a command that only prints such a line counts too, which at worst closes a site as before this decision, while reading too little would hold a researcher's record back for good. A refusal only `fetch_url` met closes nothing: a real marketplace refused every fetch and opened with prices in the browser through the run's proxy. A block page, a sign-in, or a check the browser could not pass in its bounded tries closes the site and work goes on (operator decision 2026-11-20). A site is its host without `www.`, since a shop on a portal's subdomain closed the whole portal; sources are still told apart by registrable domain. A trusted read of that host recorded after the closure opens it again, since one researcher closed a site in the same seconds another was reading a card there: a finding quoted on its stored page, at an address the page itself shows, that is no block page, whenever the store first kept that page; a later record closes it once more, and every record stays. Later researchers receive the closed sites, and `fetch_url` refuses them. Third-party readers, mirrors and proxies other than the run's own cannot work around a block: the checks cannot read that evidence. A closed site closes only itself, never its question: a site of another kind that states the answer in its own text answers it, and the gap check asks for one first (decision 2026-11-03: tax research named no pending bill). Other runs keep their handoff.
- A finding is an append-only record the moment it is made: a correction supersedes, and nothing is deleted while the run lives, so no send back or rewrite can lose one (a real run went from 15 findings to 0). A cell recorded as nothing found counts as filled.
- A report rests on records (decision 2026-11-02). A draft names record ids and the server fills its findings from them: a real run's model, retyping them, listed 9 of 56, so the checks read the maker's specifications while the prices, sellers and reviews behind the pick went unread. The report check reads fields, so what they cannot show stays the model's word (`lib/server/research/reportCheck.ts`). A pick is a row of the matrix, or the report says the data does not separate the rows and what would decide. With no report the server builds the answer from the records: it picks nothing and says so, and it outranks narration, since nearly every run has a line of it by then, but a text of report length stands, with its note, because a report outranks a digest.
- The answer opens with the draft's summary, which the server puts above the report, since most readers stop there (operator decisions 2026-11-02). It names the options it recommends as matrix rows, the pick first; a draft without one, or whose summary names no row while the draft picks one, goes back. Where the plan marked key specifications or priorities, so the user chooses, a draft that picks no option goes back too, for a default named as one (2026-11-03): on acceptance run 3 a purchase answer advised buying nothing because no option had passed every check. Rows rest on no single listing: a real run whose marketplaces were closed fell back to makers' catalogs and kept two lookalikes of one price. A purchase aims at five options across price tiers, with an offer for each it recommends from any shop; no site is named in code or prompts.
- A pick stands on checked key facts (operator decisions 2026-11-02): a real run's pick rested on a layer claim its verifier rejected, while sellers disagreed on its load and height. Only the key specifications the plan marks, of the options a draft recommends, need a second site; a round confirming one fills a cell. Disagreeing sites are both cited and named. A pick on a rejected key fact goes back within the verifier's cap.
- What the user states outranks the 2026-11-02 rule that price breaks only a tie (operator decision 2026-11-05): a user who asked for value got a pick over twice the price of a comparable option, with no record of what the extra bought. What the user's own message names as mattering is a priority the plan marks, never one added on the way. The pick, a default included, is the best fit to the priorities among options whose key facts passed; price breaks only a tie where the user named none. Under a value priority a dearer pick says from a record what the extra money buys, or the cheaper option is the default. The summary answers each priority in a line the server puts right under its text, inside the summary. The report check sends back an unanswered priority, and a dearer pick whose answer names no cheaper row where the offers read as prices in one currency; other figures stay the model's word.
- Ratings count, for products and services alike, doctors included (operator decision 2026-11-05): a person looks at the score and the number of ratings first, yet on two reviewed runs a shop's few reviews carried a pick while a marketplace's score from thousands stayed out. Where the user chooses among options, the frame holds a ratings criterion, the plan's or one the server adds in the plan's language when the frame is built; a knowledge question gets none, and a stored frame keeps what it had. A rating is a checked record with its sample: a finding with its score, scale, number of ratings and what they count, its platform the site of its link and its date the record's. Its quote holds the score and the count as the page writes them, and one that does not keeps the word of a wrong quote. Researchers take the place with the most ratings for that exact option, and the seller's own where that is what they reach, and say when a card merges variants. A rating counts with its sample (operator decisions 2026-11-05): 4.8 from thousands outranks 5.0 from seven, so an option is compared by its rating from the most ratings, pulled towards a neutral score when few gave it (`RESEARCH_RATING_WEIGHING`), and a seller's own page is shown, never compared, where a platform with more ratings rates it. A pick rated clearly below another option the summary recommends says why there, naming that option's score and count, or goes back within the report check's cap; the reason stays the model's word. The worst reviews come first, since a reviewed pick fell to one owner's report of sagging within a month that the user found alone: each recommended option has its lowest-rated reviews recorded under the ratings criterion, or not_found, and the gap check asks once for one with neither. The table gives each option's score with its count and platform, the summary the pick's, a small sample in counts and the main complaints beside it. A doctor's or a clinic's rating stands beside the qualification from official sources and never replaces it.
- Plan questions run at once and none waits for another: a real run's question on the finalists' reviews waited 12 minutes for their names. What needs the options found is a criterion a later round fills.
- Research ends on what it finds, not on time: a real run went round for 70 minutes, each send back asking for one more detail. Holes in the matrix plan each round, and only the additions an agent makes with their reasons change it. Every gate has a cap on send backs, and past it the draft goes on as it stands. The cap counts across an approval, since a person's Allow buys no checks; rounds with no new cell count afresh, as the clock does (decision 2026-11-02). A round's failed turns count too (`createResearchRounds`). A record under a key the matrix lacks is kept, never refused, and a frame with no rows has one cell per criterion, so a knowledge question has cells too. Every researcher keeps `record_evidence` and `change_research_frame` whatever its tool groups, since a custom researcher that cannot record fills no cell and research would read that as exhausted; a gate's turn never has them.
- Page texts live with the run and go with it (`agent_docs/ARCHITECTURE.md`), so a check reads what the researcher saw.
- A researcher's turn is one short task with its own call budget, records and frame changes not counted; past it the turn writes its report, and a new task goes to a fresh researcher (decision 2026-11-03, `RESEARCH_TASK_LIMITS`): on acceptance run 1 both rounds ended on the turn's time, and a continued researcher carried its old context into its new brief. One task covers one row. The calls that start sub-agents take batch places of their own (`EngineTool.delegated`), so a round runs its researchers side by side: four at a time, fifteen took eleven minutes on acceptance run 2. Accepted cost: one chat then makes up to eight researchers' model calls and their page reads at once.
- Options are noted with the page that names them, and the server counts the sites behind each, one option whatever size a listing writes with its name; agents leave the kind of product out of a label, since a word before a model may be another model's name (decision 2026-11-03, `lib/server/research/candidates.ts`): where the user chooses among options or asks for every item of a class, the items of a kind within a period included, round 1 is two or three enumeration tasks, one per kind of source, that note every option their pages name and add no rows, and the main agent adds rows from the pool's top, then sets aside with a reason each frequent one it does not take; the gap check asks once about a frequent one still open. On acceptance run 1 the researcher that saw the reference pick had no task to add rows and never named it; on run 2 one enumeration task made every row from the first pages it opened. Only the main agent sets one aside.
- A research starts with the options earlier research on its branch recommended, each accepted report's pick and summary rows, as candidates with their page and date (operator decision 2026-11-05, `lib/server/research/earlier.ts`): a real chat's second research never named the first's best option, which fitted its budget, and the user was not told. Only the branch's own turns count, and nothing links the runs. They lead the pool outside its limit, and the gap check asks once about each still open; the answer says what became of each, a row or one sentence why it went, an old figure with its date. Old records prove nothing new: a pick needs this research's records, and one not reached again stays in the reserve with its date.
- A researcher's context keeps its newest pages whole and turns older ones into stubs naming the handle that reads them back, with no model call (decision 2026-11-02), at the documented default marks of Anthropic's context editing (2026-11-03): a lower guessed mark did not hold, since most of a long thread's input is replayed reasoning and call arguments, which clearing never removes. Its thread's transcript records the stubs, so a replay reads the same context; other sub-agents keep theirs whole.
- A claim that stands for a record is judged on its stored page, since `fetch_url` cannot open many pages only a browser reached and extracts a page differently; only a record with no stored page stays could not check. Last comes the skeptic, which tries to refute the conclusion, and only what an opened page shows counts. A finding goes back within the cap, researchers closed or not, since it needs none, and stays named in the answer until the skeptic itself finds it answered.
- The answer carries no process notes, even collapsed (decision 2026-11-02): they mean nothing to its reader, and what could not be reached belongs in the report's text, where it matters. Beside the plain word that it is incomplete or not fully checked (`lib/server/research/notes.ts`), it names the skeptic's finding and each fact the checks rejected, by its record's option and criterion, while the final draft rests on that record (`lib/server/research/verifier.ts`). A claim behind a recommended option that its source bears out only in part goes back for narrower wording within the verifier's cap, and past the cap the answer names that fact the same way (decision 2026-11-05: a review was called one of the exact model when it named none). The user reads none of the checker's own words, since it read untrusted pages.
- A finished research gives a page beside its report, and the report as Markdown (operator decisions 2026-11-05): a long report takes long to read. Reports differ, so no template fits them: the main agent writes each page with `create_artifact` from the final report alone, with no Search, by a detailed guide that ships in code because the product has no system Skills (`lib/server/research/pageGuide.ts`). The answer's notes on rejected or partly supported facts and evidence against the conclusion go beside what they name, so the page never shows the most doubtful figures as plain fact. No pictures: charts and tables are enough. The page is an ordinary private artifact, so publishing it stays the user's act; one the answer does not show is archived. The server holds the answer for that one step, saved first to its message, so a restart during it still leaves the answer; the step has its own bound, starts only if the hard end leaves room and never moves it; no artifact tool, a failed call, the bound or Stop leave the answer as it would have gone out. Only a research's real end writes one, never an approval's pause or an interrupted run.
- Roles: the main agent stays on the chat's model; an administrator may bind researchers, and the checks (gap judge, verifier, skeptic). Not set, a role runs on the chat's model, and a researcher is then the built-in sub-agent whatever the user's default or the call names, since the method's brief is its instructions; set and unusable, research is refused visibly, never run on another model. No researcher starts children (decision 2026-11-02): a real run's ran for minutes, recorded nothing, and their parent redid the work. Model names live in settings, never in code. Not everyone has two models, so a check may run on the report's own model: a separate context is still useful, and the answer names no model either way (decision 2026-11-02).
- Nothing restarts by itself: only the user's Continue picks research up from what was recorded, and only on the interrupted run of its own branch. A research run that failed, whatever failed it, counts as interrupted, and so does a run sent with Deep research that failed before its start (operator decision 2026-11-06): a production research lost its last request to a provider after half an hour, and its answer offered only a rerun of everything. The user's Stop never does. A Continue whose own turn never started reads back past it to the research it went on with, so its records are picked up, not started over (`lib/server/research/resume.ts`, `continuedTurn` in `lib/server/research/run.ts`). Any other new message is an ordinary turn. A Continue is a new run with its own bindings and row, linked once to the run it continues, with a fresh clock. What the gates said adds up across every Continue of a research, read back through the turns each one picked up: as with an approval, a Continue buys no checks, so caps stay spent, rejected claims stay named and an owed rebuild stays owed. A turn whose records were lost takes its part of that with it, so its caps reopen, and the log says so. With nothing recorded it starts over with the plan. So does a Continue past the chain's bound, since a further link would put the oldest records out of a reader's reach.

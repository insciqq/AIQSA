# ADR 0035: One Release Image And Tag-Driven GitHub Distribution

Status: Accepted
Amends: 0002-technical-stack-nextjs-docker-postgres, 0015-lean-local-development-harness, 0020-unified-installation-and-isolated-development

## Context

The persistent installation used separate locally built application and tools images. That reduced the long-running image contents, but made the public install and release contract harder to explain and required two image identities that always had to advance together. AIQSA now has a public GitHub release repository and needs one obvious image that a small operator can pull as `latest` or pin to an exact release.

The private GitLab repository remains the development remote. GitHub is a curated public release remote, not a mirror, and release automation should stay small rather than duplicate the local verification harness.

## Decision

- Publish one non-root image, `ghcr.io/insciqq/aiqsa`, containing the standalone Next.js runtime plus the pruned Prisma/bootstrap/maintenance dependencies and committed scripts required by one-shot installation roles.
- The default Compose file uses one optional `AIQSA_IMAGE` value for `app`, `migrate-bootstrap`, and `mcp-maintenance`. Their commands and environment remain role-specific. The public default is `latest`; one SemVer or commit tag in the same `.env` pins every role to the same build.
- Keep `docker-compose.dev.yml` as the separate source-mounted development and verification topology. Local source builds use the `release` Docker target explicitly; the operator installation does not build source by default.
- A push of a matching GitHub tag is the sole public release trigger. The GitHub-hosted workflow builds the `release` target once for `linux/amd64` and `linux/arm64`, pushes all metadata tags to the resulting multi-platform digest, and creates the matching GitHub Release only after publication succeeds.
- A stable `vX.Y.Z` publishes `X.Y.Z`, `X.Y`, `latest`, and `sha-<short>` tags. A prerelease publishes its SemVer and commit tags but does not move `latest` or the stable minor tag.
- The tag's base version must match `package.json`. Release notes are generated by GitHub and include the image tag plus immutable digest.
- GitLab remains the private normal development remote. GitHub receives only reviewed commits and explicit release refs; no mirror or force push is part of the workflow.

## Consequences

- Installation and rollback need one image setting and cannot accidentally combine app and migration tooling from different revisions.
- The long-running app container can see migration/bootstrap files inside its non-root image even though its command and environment do not invoke them. This modest image-size and least-content tradeoff is accepted for a simpler distribution contract; service privilege, secret scoping, and non-root execution remain unchanged.
- `latest` is convenient but mutable. Operators that want deliberate upgrades pin a numbered release or immutable digest in the existing `.env`.
- GitHub Actions performs release packaging, not the project's broad test matrix or provider smokes. Required local checks and disposable installation evidence remain governed by `TESTING.md` before the tag is pushed.

# ADR 0021: Admin-Managed MCP Tools Use An Isolated Runtime

Status: Accepted
Amends: 0001-product-direction-qsa, 0002-technical-stack-nextjs-docker-postgres, 0004-private-auth-entitlements-uploads-and-sharing, 0005-in-process-run-cancellation-and-active-run-gate, 0007-context-window-budget-and-trimming, 0011-explicit-next-run-control-ownership, 0020-unified-installation-and-isolated-development

## Context

AIQSA is team tooling for a controlled installation, not a public MCP marketplace. An ordinary user must not be able to register an endpoint, choose a package, edit a process command, or otherwise install executable MCP code. A team administrator connects trusted remote or local MCP servers, inspects the tools they expose, and grants each trusted server as a unit to users and groups. Activating a server means trusting all tools that server exposes rather than curating a separate per-tool allowlist.

One run may need tools from several entitled MCP servers. Some server definitions use remote Streamable HTTP URLs, while others use the common stdio configuration shape with an executable, arguments, and environment variables. Local servers are distributed in several common forms, including npm, PyPI, NuGet, OCI images, MCPB artifacts, and administrator-supplied commands. MCP Registry metadata may describe either remote endpoints or one or more package choices. AIQSA must not encode `npx` as the product's only installation model.

A subset of administrator-declared configuration fields may need a value owned by an individual user, such as that user's API key, without allowing the user to edit the MCP server definition. A user also needs a persistent personal enabled set: entitlement makes an MCP server visible and usable, while enabling it expresses that its granted tools should be available to that user's normal AIQSA runs.

Some hosted remote MCP servers require interactive authorization instead of a pasted API key. The hosted Notion MCP server at `https://mcp.notion.com/mcp` is the reference case: it requires user-based OAuth authorization, exposes standard MCP protected-resource and authorization-server discovery, supports Authorization Code with PKCE and dynamic client registration or Client ID Metadata Documents, and issues access and rotating refresh tokens. Each AIQSA user must authorize an external workspace identity in a browser; an administrator cannot replace that lifecycle with one static Notion integration token for the hosted server.

Stdio changes the application trust boundary. The MCP client starts executable code, while the long-running AIQSA application has database, session, provider, and object-storage credentials and access to the installation data network. Running an administrator-supplied MCP process inside that application container would expose unrelated application authority to third-party code. User-specific environment values also mean that a live MCP process, transport, writable state, and discovery cache cannot safely be shared across users by default.

Package-manager launch specifications introduce a second lifecycle problem. A command such as `npx -y package` may resolve and download a different package version later. A saved MCP definition therefore cannot mean "run whatever this package name resolves to at invocation time." Installation, inspection, activation, update, and best-effort rollback need an explicit revision contract.

The normal installation must remain a single Docker Compose bootstrap. A separate rootless Docker or Podman daemon, a policy broker, or an authenticated Unix-socket control plane would improve the privilege boundary, but would add installation and implementation complexity. The initial installation deliberately accepts a highly trusted ToolHive controller on the host Docker daemon and application access to its private-network control API. This means compromise of the application can transitively become compromise of the Docker host; that risk is accepted for the trusted-admin, small-installation deployment model and remains documented rather than hidden.

## Decision

### Product ownership and permissions

- MCP server definitions are installation-owned resources. Only an administrator may create, import, test, revise, enable, disable, or delete them.
- Ordinary users cannot add, edit, or clone MCP endpoints, commands, packages, arguments, environment-variable names, mounts, network policy, or tool schemas.
- MCP use is deny-by-default at the server level. Matching direct-user and group `McpGrant` rows contribute `canUse`, which authorizes the MCP server and every valid tool it exposes at run preparation. Exact `personalSlotKeys` are an independent permission allowed only on a direct-user row; a group never grants members permission to store personal values implicitly. Effective server use is the union of direct and group rows, while effective personal slots come only from that user's direct row. Either permission may exist without implying the other.
- A personal value is not a user-owned MCP connection. It is a value for an administrator-declared configuration slot on an installation-owned MCP server.
- A per-user OAuth grant is likewise not a user-owned MCP definition. An entitled user may connect, reconnect, or disconnect only their external identity from an administrator-declared OAuth-capable server; they cannot change its endpoint, authorization server policy, scopes, client metadata, redirect URI, or tool inventory.
- Backend authorization is revalidated when building the current-user catalog and accepting a run. The accepted run keeps that immutable authorization and tool snapshot until it reaches a terminal state. Disablement or grant loss prevents new runs immediately but does not interrupt or reauthorize each call inside an already accepted run; its runtime drains after active run bindings finish.
- `Disable` is the reversible way to retain a configured server without offering it to users. `Delete` is a confirmation-gated, irreversible administrator action with no user-visible archive/restore lifecycle: it immediately tombstones the server, removes it from administrator and user catalogs, blocks grants, prewarming and new runs, and turns off saved user preferences. Runs accepted before deletion may finish against their pinned generation. Ordinary reconciliation then removes the drained workloads, effective secret snapshots, OAuth connections, grants, user preferences, revisions and server configuration. Historical run snapshots, events, tool-call evidence and safe runtime fingerprints remain self-contained and inspectable; they do not keep the deleted live configuration usable. The existing nullable `archivedAt` field may implement the short internal drain tombstone, but `Archive` is not a product action.

This extends ADR 0004's entitlement direction from provider/model/search targets to MCP servers and exact personal-value slots. It does not turn AIQSA into the marketplace or generic agent builder excluded by ADR 0001.

### Server definitions, drafts, immutable activated revisions, and updates

- Each MCP server owns one mutable administrator draft and zero or more immutable activated configuration revisions. The draft contains the source, transport, normalized endpoint or launch specification, fixed arguments, declared configuration slots and runtime policy. Testing enriches that same draft with a resolved executable artifact, integrity identifiers, informational discovery evidence and a hash of the exact tested configuration. Any later draft edit invalidates that evidence. Activation requires the current draft hash to equal the tested hash and copies the complete tested state into a new immutable revision. Failed or superseded draft tests may remain bounded administration activity; they do not create permanent revision records.
- An activated revision is the only configuration identity used by runtimes and accepted runs. Runtime tool inventory is observed per user and runtime generation rather than normalized into revision/tool history tables, so one user's workspace-specific inventory cannot overwrite another's and an inventory refresh never mutates the activated revision.
- A revision stores the administrator's requested selector separately from the resolved artifact. For example, `@scope/package@^2` may remain as update intent, while execution uses only an exact package version plus integrity metadata or an OCI digest. `Check for update` resolves the requested selector again; an active revision never executes the selector directly.
- Transport, source and launcher are separate concepts. The standard transports are stdio and Streamable HTTP. Legacy HTTP+SSE is compatibility-only and requires a later adapter; it is not part of the initial supported matrix. Sources identify a remote endpoint or materializable artifact. Launchers such as `npx`, `uvx`, `pipx`, `docker`, or `dotnet` are runtime adapter details, not separate MCP product modes.
- The source model is a small discriminated configuration union rather than a framework of source, launcher, transport and artifact classes. The complete initial source set is:
  - `Remote`: initially a direct Streamable HTTP URL; legacy HTTP+SSE is deferred to a later compatibility adapter;
  - `Npm`: an npm package and arguments, including imported `npx` configuration;
  - `PyPI`: a Python package and arguments, including imported `uvx` or `pipx` configuration;
  - `OCI`: a digest-pinned container image and arguments. The initial ToolHive Compose slice supports stdio OCI workloads only with the image's declared entrypoint; ToolHive v0.40.1 does not expose a safe command/entrypoint override through the selected REST path, and native HTTP OCI remains deferred by the spike result below.
- `New server` starts with an import adapter rather than an empty expert form. The administrator may paste one remote URL, a common `mcpServers`/single-server JSON object, or one recognized `npx`, `uvx`, `pipx`, `pip install`, `docker`, or `podman` command, then reviews the normalized source before saving; manual configuration remains a secondary action. A JSON definition with a bare executable may be followed by one recognized install command, such as `pip install`, to identify the managed package source. Parsing never invokes a shell or executes the pasted text.
- The revision JSON remains extensible to MCP Registry or compatible private-registry entries and `server.json`, integrity-pinned MCPB artifact URLs, NuGet packages, Go modules, and reproducible VCS builds without normalized source-specific tables. Those source cases are added only when demanded; the initial implementation uses a direct switch over `Remote`, `Npm`, `PyPI`, and `OCI` rather than a general plugin or installer framework.
- An unknown arbitrary host command is not executed merely because an administrator pasted it. Advanced execution requires an OCI image or another supported adapter that materializes the executable inside the isolated runtime. A generic download or VCS URL additionally requires an immutable version, commit, digest, or checksum and a reproducible build recipe whose output is a pinned artifact. Direct remote MCP endpoint URLs are validated separately and are not treated as downloadable code.
- Import is an authoring convenience; an active runtime never follows a mutable package tag, URL payload, image tag, VCS branch, or unpinned package on every start.
- Local package and artifact execution has one managed workflow, not separate evaluation and production modes:
  1. testing the mutable draft resolves its package/executable to a concrete artifact and records the exact registry version, registry artifact URL and integrity plus the unique ToolHive-generated image reference, or the administrator-supplied OCI digest, beside the tested draft hash;
  2. the runner installs or materializes that artifact once; activation freezes the resolved state and runtime creation uses the tested generated image reference for package sources or the pinned digest for OCI rather than performing a fresh package-manager install for each run;
  3. AIQSA initializes the server, discovers tools, validates schemas and limits, and presents an informational server/tool diff;
  4. an administrator explicitly activates the revision, except that successful administrator validation OAuth completes testing and activation as the single expected happy path described below.
- Remote definitions use the same draft/test/activate flow, but validation connects to the endpoint, negotiates MCP capabilities, discovers tools, records normalized authentication/configuration requirements and definition hashes, and applies the remote SSRF policy instead of building a local artifact. The endpoint URL is administrator-visible non-secret configuration: URL userinfo, query strings, and fragments are rejected; ordinary routing/resource path segments remain allowed but must not contain credentials. Providers that require a secret in the URL are initially unsupported and must instead expose an encrypted static-header binding or OAuth.
- Saving a new non-OAuth server immediately performs one ordinary update-resolution/draft-test request so common imports do not require a second discovery button. An OAuth draft instead starts authorization; its successful validation callback performs the hash-fenced test and activation. Failure leaves the created draft visible and inactive with an actionable error.
- There are no automatic updates to an active MCP revision. After initial creation, an administrator action labelled `Check for update` or `Update MCP` resolves the configured selector again into the mutable draft. The current revision remains active until that exact draft passes installation, discovery, security checks and review, then activation creates the next immutable revision; no background job follows mutable registry versions or changes an active revision.
- Editing a supported source selector, arguments, fixed environment configuration, runtime policy, or transport follows the same draft/test/activate flow. Prior activated revisions remain available for audit and best-effort rollback; rollback switches `activeRevisionId` to an existing usable revision and does not create a second revision history mechanism.
- The MCP server is the trust and grant unit. Activation authorizes all valid tools returned by `tools/list`; there is no separate per-tool approval, destructive-action approval, or per-tool grant in the initial product.
- A runtime `tools/list_changed` notification marks only that user/runtime inventory stale and schedules the ordinary paginated refresh. One bounded JSON inventory is stored on the runtime generation and atomically replaced; there are no normalized per-tool rows or inventory-generation history. Inventory is otherwise refreshed on enable/reconnect, when the user opens the settings surface and cached inventory is stale, and synchronously during run preparation when its bounded freshness window has expired. No unconditional periodic `tools/list` polling is required. New and changed valid tools become available to that user's next accepted run under the existing server grant. An already accepted run retains its immutable tool snapshot. A malformed or unsupported tool definition makes the affected user/runtime identity actionably unavailable rather than silently omitting the tool or globally changing another user's server state.
- ToolHive update or registry-resolution operations are never authoritative for AIQSA activation. AIQSA owns draft testing, inspection, activation, and the exact resolved artifact; ToolHive may only materialize the artifact requested by the active AIQSA revision.
- Materialized local artifacts are retained in the Docker image cache but are not copied into a durable registry or the installation backup. Rollback is therefore best-effort: it works only while the exact recorded artifact remains present. A missing image marks the revision `Artifact missing`; `Rebuild` first copies that selected revision's requested selector and source configuration into the draft, then tests/materializes and activates it as a new revision rather than silently replacing or claiming identity with the missing artifact. If the current draft contains unrelated work, the administrator must explicitly preserve, replace, or cancel it before Rebuild proceeds. Remote rollback restores only AIQSA-owned endpoint/configuration state and cannot roll back mutable behavior controlled by the remote operator.

### Explicit configuration bindings

- AIQSA performs no implicit user-derived environment substitution. In particular, it does not automatically synthesize values such as `aiqsa:${user.id}`. Every runtime value source is explicitly configured by an administrator.
- An administrator declares exact typed configuration slots with stable opaque `slotKey` values within that MCP server's revision lineage. A slot key is a semantic identity: changing its environment/header binding target, value type, sensitivity, or personal/shared policy requires a new key, and prior grants or values are never transferred automatically. Friendly labels and validation bounds may evolve under the same key; a newly invalid current value makes readiness actionable. A slot may use an admin literal, an admin shared secret, a personal value that is optional with an explicit shared fallback, or a required personal value. Grants and encrypted envelopes reference only stable keys; unknown or removed keys are ignored for effective configuration and are never rebound by display name. The initial release has no separate stale-envelope cleanup UI: an inactive encrypted entry may remain in its existing envelope until the parent row is eventually removed or later retention work handles it, but it is not returned to the browser, selected for runtime configuration, or exposed as run evidence.
- When testing a draft that declares a required personal slot without a shared fallback, the admin test form accepts a one-time validation value. It exists only in the test request and disposable validation session or workload, is never saved as a shared/user value or copied into the activated revision, and is discarded with that test state. The accepted ToolHive plaintext-exposure and cleanup limitations still apply while a local validation workload exists.
- A slot targets one administrator-selected process environment variable or HTTP header. The initial implementation does not interpolate user or secret values into URLs, commands, arguments, filesystem paths, or shell expressions.
- An ordinary user may set, replace, or clear only the value of a slot for which that user has a current personal-value grant. The user cannot choose the environment-variable or header name or move the value to another binding target.
- Each personal slot declares a type, validation, bounds, and sensitivity. Secret values are field-scoped and write-only; responses expose only presence, source, revision, and timestamps. Non-secret strings, enums, numbers, or booleans may be returned to their owner when the administrator marked the slot non-sensitive. AIQSA encrypts authoritative secret records with AES-256-GCM, a fresh nonce per record, and one dedicated installation key supplied as base64-encoded 32-byte `AIQSA_ENCRYPTION_KEY`; the stored envelope carries a format version but the initial product has no online keyring or automatic rotation. The auth session/flow-signing secret is not reused for this encryption, and the operator must back up the encryption key separately from Postgres. Changing it requires a planned offline migration or re-entry of affected secrets. The plaintext ToolHive execution state for local environment bindings is the explicit exception documented below.
- When accepting a new run, a configured personal value takes precedence only while its grant remains valid. An invalid personal value does not silently fall back to a shared external identity. The user must explicitly clear it to select the shared value. An already accepted run remains pinned to the runtime generation that contains its encrypted effective static-configuration snapshot.
- Runtime-control variables such as executable search paths, loaders, language runtime injection, package-manager configuration, and equivalent process-control settings cannot be user-overridable.
- Current administrator/shared values and each user's current personal values are stored as small versioned encrypted envelopes rather than one immutable database record per slot version. Creating a desired runtime generation resolves the authorized effective values and copies them into one encrypted `effectiveConfigEnvelope` owned by that generation. Changing or clearing a value increments the applicable envelope version, fences it from new runs, and schedules a new runtime generation. The prior runtime generation retains the old encrypted snapshot only while a non-terminal accepted run binding references it; after drain reconciliation stops its workload/session and deletes the disposable generation row, `ON DELETE SET NULL` clears the binding's live reference. The binding retains only its safe immutable generation fingerprint for historical evidence. This replaces separate credential-generation, tombstone, reference-count and lease subsystems.
- Remote API-key and static-header authentication uses the same typed-slot rules. An accepted run stores only an opaque runtime-generation binding; the common MCP client decrypts that generation's effective snapshot for the exact outbound session. Remote static values are not sent to or persisted by ToolHive in normal operation. Interactive OAuth is a distinct authorization lifecycle rather than a header-slot override and follows the contract below.

Environment defaults are configuration conveniences, not authorization boundaries. When an MCP tool accepts tenant, account, repository, user, or workspace identifiers in its arguments, isolation must come from the external service's authorization or an explicit reviewed AIQSA argument-binding policy. It must not be inferred from an environment default.

### Per-user OAuth for remote MCP servers

- OAuth is a revision-owned remote authentication mode alongside unauthenticated and typed static-header modes. The administrator selects or accepts the discovered mode and inspects the endpoint, protected-resource identity, authorization-server origins, requested scopes, redirect policy, and discovered tool inventory. An ordinary user cannot override any of them.
- AIQSA supports the MCP HTTP authorization profile generically rather than hard-coding Notion, but does not reimplement its discovery, PKCE, dynamic-registration, token-exchange or refresh protocol. The official MCP TypeScript SDK owns protected-resource and authorization-server discovery, Authorization Code with S256 PKCE, the `resource` indicator, dynamic client registration, refresh grants, and Client ID Metadata Documents where an installation can publish a suitable HTTPS document. AIQSA supplies the SDK's OAuth client-provider callbacks for reviewed policy, durable registered-client reuse, encrypted token storage, redirect completion and serialized persistence.
- Hosted Notion MCP is the reference interoperability target. Draft activation uses a dedicated administrator validation connection or another trusted source to verify protocol compatibility and inspect the current tool inventory; the validation connection is an ordinary row in the same OAuth-connection model with an explicit validation purpose, is revocable afterward, and is never a runtime fallback. AIQSA never borrows an ordinary user's OAuth tokens for administrator validation. Per-workspace plan or tool availability is rechecked for each user and may only affect what that user's server session exposes.
- Remote endpoint, OAuth discovery, registration, token, and revocation requests use an SSRF-hardened HTTP client. HTTPS is required outside explicit local development; configured and discovered origins are validated against revision policy; private, loopback, link-local, and metadata destinations are denied unless an administrator explicitly approved an internal target; DNS is rechecked at connect time; redirects cannot leak credentials across origins; and an MCP-audienced access token is sent only to the reviewed canonical resource.
- Installation client identity and user authorization grants are separate records. A reusable dynamic client registration or metadata-document identity belongs to the AIQSA installation and redirect-URI revision. Access tokens, refresh tokens, external subject/workspace identifiers, granted scopes, and expiry belong to one AIQSA user or explicit administrator-validation purpose, MCP server, and OAuth-policy fingerprint. That fingerprint covers the canonical protected resource, allowed authorization-server origins, scopes, client identity, and redirect identity. A later MCP server revision may reuse the connection when this fingerprint is unchanged; unrelated command, artifact, slot, or display edits do not force OAuth reconnection.
- `Connect` creates a short-lived authorization transaction bound to the authenticated AIQSA user or validation purpose, OAuth-policy fingerprint, redirect URI, random `state`, PKCE verifier, and one exact configuration identity: `activeRevisionId` for a user connection or the current `testedDraftHash` for pre-activation administrator validation. It reuses the existing signed, HttpOnly, short-lived OAuth flow-cookie pattern unless an interoperability requirement proves durable server-side flow storage necessary; the callback revalidates the current authenticated user and refuses completion if that revision is no longer eligible or that tested draft hash/policy has changed, then consumes/clears the flow. After activation the validation connection may be reused only through the same OAuth-policy fingerprint. Production callbacks use HTTPS. Tokens are exchanged server-side and are never stored in browser local storage, cookies, URLs, or client-visible API responses.
- OAuth completion settles the action the administrator or user actually started. For administrator validation, a successful callback rechecks the flow-bound draft hash, tests that exact draft with the new connection, and activates the resulting tested revision; any test or activation failure returns a generic failed outcome and leaves the draft inactive. For an entitled user, a successful connection or already-connected `Connect` path enables that server preference and kicks asynchronous reconciliation. Reconnect has the same settlement semantics. The browser receives `connected` only after this settlement succeeds; that outcome means authorization and the requested enable/activation state were accepted, not that the asynchronous runtime is already `Ready`.
- OAuth tokens and any dynamic client secret use the same dedicated AES-256-GCM application encryption facility. Responses expose only connection presence, external workspace/account labels approved for display, scopes, expiry/readiness, and timestamps. The AIQSA integration does not intentionally place raw tokens in run snapshots, ToolHive state, logs, events, or provider prompts.
- The SDK performs the refresh exchange while AIQSA owns its concurrency and persistence boundary. Routine access/refresh-token rotation is singleflight per connection, persists the rotated material atomically inside the same connection revision, and does not drain a healthy MCP session. Reconnect or a change of external subject/workspace, scopes, protected resource, client identity, or redirect identity creates a new connection revision and drains the old one. `invalid_grant`, revocation, absolute expiry, or an unrecoverable client mismatch clears readiness and produces `Reauthorization required`; it is never retry-looped or silently replaced with another user's or shared identity.
- `Disconnect` marks the OAuth connection unavailable for new runs, defers provider revocation and encrypted-token deletion until every non-terminal accepted run binding using it has drained, then cleans up its sessions. Safe account/audit metadata may remain, but no historical runtime row or secret is retained merely for the binding. It leaves the installation-owned server definition and grants unchanged. Merely disabling the MCP preserves the connection so re-enabling need not prompt again. Loss of the final entitlement, user removal, or server archival likewise prevents new runs immediately while retaining only the material needed by already accepted run bindings until drain.
- OAuth connection readiness is separate from entitlement, persistent enablement, and runtime health. An entitled OAuth-backed server may be `Needs authorization`, `Authorizing`, `Ready`, or `Reauthorization required`; only a current ready connection may contribute tools when accepting a new run, while an already accepted run remains pinned through its runtime-generation binding to the selected connection revision.
- Notion-specific token lifetimes are provider behavior, not constants in this ADR. The implementation honors returned expiry values, persists every rotated refresh token, serializes concurrent refresh attempts, and expects periodic user reconnection. Mutable provider facts and interoperability observations belong in `PROVIDER_API_NOTES.md`.

OAuth requirements and current Notion behavior are documented in [Notion's custom MCP client guide](https://developers.notion.com/guides/mcp/build-mcp-client) and [Notion's hosted MCP connection guide](https://developers.notion.com/guides/mcp/get-started-with-mcp).

### Isolated MCP execution boundary

- The long-running Next.js application remains the control plane and owner of authentication, grants, encrypted configuration, run preparation, provider orchestration, and durable audit metadata.
- AIQSA uses the current stable [official MCP TypeScript SDK](https://github.com/modelcontextprotocol/typescript-sdk/tree/v1.29.0) as its only MCP client-protocol implementation, pinned to an exact reviewed dependency version behind one narrow `McpClientSession` wrapper. The SDK owns JSON-RPC correlation, initialize/initialized lifecycle, Streamable HTTP framing, MCP session headers, notification dispatch, protocol cancellation, timeouts and OAuth protocol helpers. AIQSA does not implement a second JSON-RPC, Streamable HTTP, session or OAuth client stack. As of this decision the production line is v1.x; a later v2 migration changes the wrapper, not product policy or persistence.
- Local and remote execution converge on the same SDK `StreamableHTTPClientTransport`. A remote definition supplies its reviewed URL, SSRF-safe fetch and static/OAuth auth provider directly. `ToolHiveMcpRuntimeDriver` owns only local workload lifecycle operations—create/start, list/status, restart, stop/delete, and retrieval/normalization of the private proxy URL—after which the same `McpClientSession` talks to that proxy. Neither endpoint origin is exposed to the model or browser.
- The ToolHive lifecycle client is a small handwritten adapter for only the workload endpoints AIQSA uses, with minimal response-shape validation. AIQSA does not generate or carry a complete ToolHive OpenAPI client and does not let ToolHive become the semantic MCP client. Draft validation may read a tightly bounded workload-log response after a failed local startup, classify a small allowlist of actionable conditions such as a missing uppercase environment-variable name, and then discard it; raw or unclassified process output is never returned through an AIQSA API or persisted as validation evidence.
- Stdio processes never run inside the Next.js application container or directly inside the ToolHive service container. They run as separate sibling workload containers and receive only their exact administrator-declared MCP configuration bindings: no database URL, LLM-provider credentials, auth/session secrets, object-storage credentials, uploads, unrelated MCP credentials, host filesystem, or container-engine socket.
- MCP workloads must not be privileged, receive host mounts or devices, join host PID/network namespaces, add capabilities, or reach the Docker/Podman socket. They receive isolated ephemeral working state but ordinary outbound Internet/LAN access because common MCP servers must call external services. The first release does not claim egress allowlisting or network isolation beyond keeping workloads off the AIQSA application/data networks. Application-layer startup/call timeouts and input/result-size caps are mandatory. Container-enforced read-only filesystems, non-root execution, no-new-privileges, CPU, memory, process, file, idle, and maximum-lifetime ceilings remain optional later hardening rather than release blockers.
- For local execution, the application communicates with ToolHive over an unauthenticated TCP API on a dedicated non-published Compose network. The initial release deliberately does not add a Unix socket, OIDC service authentication, or a policy broker. The API must never be host-published or browser-accessible. The application sends only AIQSA-generated workload requests in normal operation, but this code-level discipline is not a security boundary: compromise of the application may exercise the full ToolHive API and thereby compromise the Docker host. The runtime is not a second business backend and does not query the AIQSA database.
- ToolHive is selected as the initial Docker Compose backend for local executable/stdin MCP servers. AIQSA depends on the narrow workload-lifecycle adapter plus the common MCP SDK session wrapper, so an AIQSA-specific supervisor or a different local backend can replace ToolHive without changing catalog, grant, configuration, run-snapshot, provider-loop, or UI contracts.

This is a narrow amendment to ADR 0002: a separate execution service is justified by the third-party-code boundary, while application business logic remains in the TypeScript/Next.js/Postgres modular monolith. It also amends ADR 0020 by permitting an isolated MCP runtime component in the normal installation topology when MCP is enabled; it does not create a second environment tier or a second source of product state.

### Initial MCP protocol scope

- The initial client supports stdio indirectly through ToolHive's Streamable HTTP proxy and supports validated remote Streamable HTTP directly. The pinned official SDK implements the protocol path needed by common servers such as hosted Notion, API-key-backed productivity services, and `npx`/`uvx` servers: `initialize`, the initialized lifecycle, `ping`, `tools/list`, `tools/list_changed`, `tools/call`, transport sessions, timeouts and best-effort cancellation.
- AIQSA adds only a bounded `listAllTools` helper that follows every pagination cursor. A `tools/list_changed` notification marks the runtime inventory stale and invokes that same helper instead of trusting a one-page SDK convenience refresh. One live SDK client belongs to one runtime generation and safely correlates bounded concurrent calls; AIQSA does not build another MCP request/session state machine or persist transport session IDs unless a tested supported server proves crash-spanning session continuity necessary.
- AIQSA initially exposes only MCP tools. It does not advertise or implement roots, sampling, elicitation, experimental tasks, or arbitrary server-initiated model calls. MCP prompts and resources do not automatically become AIQSA product features.
- Tool definitions are normalized into one canonical AIQSA representation. Arguments produced by a model are parsed strictly and validated against the exact snapshotted input schema before dispatch; malformed JSON, unknown tools, oversized values, or unsupported schemas fail actionably and are never coerced to an empty object.
- Initial tool results support bounded text and structured JSON. Images, audio, embedded resources, resource links, remote icons, and local or remote URIs are not fetched automatically or injected into the model; unsupported-only results produce a bounded tool error. These result types may be added later without changing the transport or grant model.
- Tool results and errors are untrusted MCP output. A bounded raw result exists only in call-local memory, then AIQSA normalizes it and applies exact-known-secret redaction before durable persistence. The durable result is the same bounded redacted continuation payload later submitted to the provider and used for diagnostic previews. AIQSA cannot guarantee that a trusted MCP will not transform, log, return, or exfiltrate a credential it legitimately received.

### ToolHive Docker Compose topology

The initial installation uses Docker-outside-of-Docker, not Docker-in-Docker:

```text
Docker host daemon
├── aiqsa-app
├── postgres
├── minio
├── toolhive-runtime
│   ├── thv serve
│   └── ToolHive proxy/supervisor processes
├── mcp-<opaque-workload-id>
├── mcp-<opaque-workload-id>
└── ToolHive-managed network helpers where required
```

- `toolhive-runtime` is a dedicated Compose service using a pinned official image version or digest, persistent ToolHive state, an internal control network shared only with the AIQSA application, and access to the host engine socket. It sends Docker API operations to the host daemon and creates sibling containers; it does not run an inner Docker daemon.
- Only `toolhive-runtime` receives `/var/run/docker.sock` or the selected equivalent. A read-only bind flag does not make the Docker API read-only. The AIQSA application, migration/bootstrap tools, Postgres, MinIO, and every MCP workload receive no engine socket.
- Access to the host socket makes `toolhive-runtime` a root-equivalent trusted infrastructure component capable of inspecting or controlling sibling containers. Because the application can call the full private ToolHive API, application compromise is transitively host compromise even though the application has no socket mount. This accepted risk is not mitigated by the TypeScript driver abstraction. In normal configuration AIQSA does not intentionally mount or inject its database, session, LLM-provider, SMTP, OAuth, or storage credentials into ToolHive and sends only the exact local-MCP environment bindings required for a workload generation; a compromised controller can nevertheless obtain broader authority through Docker. Its image is pinned and upgraded deliberately.
- A separate rootless Docker/Podman daemon would give a stronger boundary, but is deliberately deferred to preserve the one-command Compose bootstrap. Docker-in-Docker is not used. A later rootless deployment changes only the runtime driver endpoint and installation wiring.
- The unauthenticated ToolHive API and per-workload proxy endpoints are not published to the host. They bind only as required on a private MCP control network reachable by the application. No Unix socket, policy broker, or service-authentication layer is required in the initial topology. Browser clients and ordinary users never address ToolHive directly.
- MCP workload networks are distinct from the application data network. A workload never joins the Postgres/MinIO network merely to reach its proxy, but it has ordinary outbound Internet/LAN access with no AIQSA egress allowlist in the initial release. AIQSA-generated names, labels, ownership markers, and structured log fields do not disclose a user email, external account, secret, or raw user ID; arbitrary MCP output and stderr remain untrusted.
- For `npx://` and `uvx://` sources, ToolHive materializes an OCI image and launches the resolved server in a sibling container. An OCI source launches its pinned image directly. A local stdio proxy attaches to the workload's stdin/stdout through the Docker API and exposes an internal HTTP MCP endpoint. Validated remote Streamable HTTP, including OAuth-backed servers, creates no ToolHive workload or proxy by default; the common SDK session connects to the reviewed remote URL directly.
- AIQSA continues to treat personal and administrator/shared credentials as product-level secrets: they are encrypted at rest in Postgres, write-only in user-facing APIs, exact-known-value redacted in AIQSA-controlled logs and evidence, and decrypted only while preparing an exact authorized workload generation. Marking a ToolHive binding as ordinary `env_vars` is an implementation transport choice and never changes the slot's sensitivity, visibility, or authorization semantics.
- The initial ToolHive integration sends an effective local-MCP secret through the private workload API as an ordinary environment value. ToolHive persists and returns that value in its workload state, and the Docker daemon records it in container environment metadata. This is an explicit trusted-host compromise, not a claim that Docker encrypts or conceals environment variables.
- The accepted trust boundary assumes that the application, Docker-host administrators, Docker daemon, and dedicated ToolHive controller are trusted with active local-MCP credentials and runtime control. Ordinary AIQSA users, browsers, unrelated application services, and other MCP workloads receive no ToolHive API access, engine socket, shared process namespace, or raw workload configuration. A ToolHive encrypted secret provider would reduce exposure through ToolHive state and API responses, but would not hide an environment-injected value from the host Docker authority; absence of a headless provider is not a release gate and AIQSA does not carry a ToolHive fork for it.
- Plain environment transport has mandatory application-side hygiene. ToolHive control and proxy endpoints remain private; AIQSA does not intentionally log or return raw workload requests, secret bindings, OAuth material, or process environments; exact known secret values are redacted at diagnostic boundaries; workload and binding identifiers are opaque; and ToolHive state, Docker metadata, backups, and diagnostics are handled as sensitive installation data with restrictive access and encrypted or excluded backups. A selected MCP can still log, return, transform, or exfiltrate a credential it receives. Installation documentation must disclose both that trust and the ability of an application, host, or Docker administrator to inspect local-MCP credentials.
- Rotation, clearing, grant loss, disablement, user removal, and revision replacement fence the old runtime generation for new runs, retain it only while a non-terminal accepted run binding references it, then drain and delete its workload and encrypted effective-configuration snapshot. Cleanup is reconciliation-dependent and is not represented as immediate revocation or forensic erasure from prior storage or backups. Remote static and OAuth credentials are sent only by AIQSA's common SDK session and are not sent to or persisted by ToolHive in normal operation.

Postgres is the sole desired-state and audit source. ToolHive state is sensitive but disposable observed execution state; its plaintext environment cache is never used to reconstruct catalog revisions, grants, user preferences, or credentials. Every workload has an opaque AIQSA owner token and runtime-generation fingerprint derived from server revision, user scope, OAuth connection revision, and the canonical effective slot vector. Each vector item contains only `slotKey`, the selected source (`literal`, `shared`, `personal`, or `missing`), the selected value-envelope version, and the authorization result—not the value itself or unstable grant-row IDs.

AIQSA performs idempotent startup and periodic reconciliation, and triggers it after enable/disable, configuration change, grant change, revision activation, relevant authenticated session activity, or either side's restart. Reconciliation:

1. computes desired runtime generations from current Postgres state;
2. lists only workloads carrying an exact AIQSA ownership marker;
3. adopts a matching healthy current generation or creates the missing one;
4. restores a lost ToolHive proxy even when its workload container survived;
5. drains stale, revoked, disabled, duplicate, and unbound prior runtime generations;
6. removes AIQSA-owned orphans after a bounded grace period and never adopts unknown containers;
7. conditionally updates only the matching `McpRuntimeGeneration` row's readiness timestamp, stable error code, retry time, and bounded attempt count; the fingerprint prevents a late result from updating a newer desired generation.

The initial single-replica `aiqsa-app` owns two small process-local periodic loops: the MCP runtime coordinator and the existing checkpointed provider-run recovery scheduler. Keeping those concerns separate avoids introducing a general scheduler abstraction merely to share one timer. Startup and relevant mutations call the coordinator's idempotent immediate `kick`; `retryAt` and an attempt count provide capped backoff. Recent authenticated presence is derived from existing session activity such as `AuthSession.lastSeenAt`, not a separate presence-lease model. No queue, jobs table, Redis, worker service, leader election, or general workflow engine is introduced. A future multi-replica deployment requires database leases or external ownership before more than one application replica may run either loop.

Dynamic sibling containers do not belong to the Compose project, so `docker compose down` cannot be trusted to remove them. The initial standalone process adds no signal-specific workload drain: a controlled coordinator stop closes its MCP SDK sessions, while startup reconciliation and periodic garbage collection are the normal correctness boundary after an application or host restart. Installation operations expose one exact-marker cleanup command for planned uninstall or manual recovery; it removes only AIQSA-owned workloads and can verify that none remain. ToolHive never becomes the source from which desired state is reconstructed.

### Minimal persistence shape

The initial persistence model deliberately combines related lifecycle state instead of normalizing every intermediate concept:

- `McpServer` owns display metadata, an internal deletion/drain tombstone, `activeRevisionId`, one mutable draft with tested hash/evidence, and the current versioned encrypted administrator/shared-value envelope.
- `McpRevision` contains only immutable activated configuration, resolved artifact and validation evidence. Source, transport, slot definitions, auth policy and integrity metadata are bounded typed JSON inside this row rather than separate source, transport, slot or artifact tables.
- `McpGrant` is one direct-user-or-group row. Both row kinds may grant `canUse`; only a direct-user row may contain exact `personalSlotKeys`, and it may grant those slots without granting server use. Effective server access is the union of matching direct and group rows, while effective personal-slot permission comes only from the user's direct row. This preserves the separate permissions without two grant subsystems or per-tool grants.
- `McpUserServer` owns the persistent enabled preference, current versioned encrypted personal-value envelope and desired runtime-generation reference for one user/server pair.
- A small installation-scoped OAuth client record caches reusable registration/client metadata, while `McpOAuthConnection` stores one user or explicit administrator-validation connection and its encrypted rotating tokens. The existing short-lived signed flow-cookie pattern owns start/callback state; no general OAuth workflow table or service is introduced initially.
- `McpRuntimeGeneration` combines one user/server/revision fingerprint, nullable encrypted effective static configuration, OAuth connection reference, disposable runtime handle, bounded current inventory JSON, readiness state, stable error, retry time and last-used evidence. More than one live materialized generation exists only when non-terminal accepted runs still bind an old one; after drain the entire disposable row may be deleted.
- `McpRunBinding` links one accepted model run to each exact runtime generation it may use. It stores only an immutable `runtimeGenerationFingerprint` and a nullable `runtimeGenerationId` with `ON DELETE SET NULL`. While the owning `ModelRun` is non-terminal the live reference is the drain guard and server/runtime mapping; the existing terminal run status makes it safe for reconciliation to delete the generation. No separate release marker is needed. The exact safe namespaced tool definitions remain in the existing immutable `ModelRun.normalizedRequest`, so they are not duplicated into normalized tool rows.
- `ModelRunToolCall` stores each dispatched provider call's round, ordinal, provider call ID, namespaced tool identity, bounded arguments, state, normalized/redacted result and timestamps. It is unique by run, round and provider call ID and is the only new per-call state table.
- `ModelRun.toolLoopState` is one small versioned JSON checkpoint for the current phase, round, bounded provider continuation and provider cursor when required. Existing `providerResponseId`, `ModelRunEvent`, `UsageEvent`, request preview and terminal fields retain their current ownership.

There are no separate persistence models for slot definitions, source adapters, materialized artifacts, tools, inventory generations, credential generations, runtime leases, presence leases, readiness labels, provider rounds, reconciliation jobs, or hard-delete jobs. Administrator deletion uses the existing server timestamp only as a temporary internal tombstone. The ordinary reconciler drains accepted bindings and then deletes live runtime/configuration/OAuth state and the server graph; retained run snapshots and tool-call evidence do not require a live server or revision row. No second archive/restore product lifecycle or dedicated deletion queue is introduced.

### Runtime identity and lifecycle

- An enabled MCP server receives its own runtime generation and live SDK client. Several enabled MCP servers therefore produce several independently routed clients or processes; no single stdio stream multiplexes unrelated servers.
- Runtime identity always includes the activated server revision, user ID, OAuth connection revision, and canonical effective slot vector after grants and fallback selection. Each slot contributes its stable key, selected source, selected value-envelope version and authorization result, but never plaintext, ciphertext or a grant-row ID. This also applies to unauthenticated servers and shared administrator credentials. A local process, remote `Mcp-Session-Id`, notification stream, writable home/temp state, and tool-inventory cache are never shared across users. Only a stateless low-level HTTP connection pool may be shared. The SDK may establish a fresh MCP transport session after application restart; persisting transport session IDs is deferred until a tested supported server demonstrates that crash-spanning continuity is necessary.
- Enabling a server, changing one of its personal values, connecting/reconnecting an OAuth identity, replacing an OAuth connection revision, activating a new server revision, or restoring runtime availability kicks asynchronous reconciliation. Routine token refresh inside the same connection revision does not. The control plane validates effective configuration, creates or selects the desired runtime generation, asks ToolHive to start/restart a local workload where applicable, and asks the common SDK session to connect and health-check without waiting for a Send action.
- While a user has recent authenticated UI activity, a best-effort prewarm policy keeps that user's enabled servers ready. Login, opening the application, returning to a visible tab, authenticated API activity, and a bounded periodic status poll update existing session activity and kick reconciliation. Multiple tabs coalesce into the same deterministic desired runtime identity rather than creating duplicate processes. Session-activity expiry and idle policy allow unused runtimes to be evicted. Presence is derived optimization input, never a separately persisted lease, an authorization fact, or the only startup path.
- The initial runtime model is always per-user with asynchronous prewarming, reuse across that user's runs, and idle eviction. It has no shared-installation-process mode and no alternate per-run process mode. This single identity rule deliberately trades more processes for simpler isolation and lifecycle behavior.
- Send-time preparation still revalidates grants, credentials, revision and observed readiness because a prewarmed process or remote endpoint may fail at any time. This guard may reconcile an unexpectedly lost runtime, but normal startup latency is moved to enable/change/session-resume time rather than first tool use.
- Several tools from one server in one run reuse that run's `McpRunBinding` and SDK client. The official SDK preserves request IDs and permits bounded concurrent calls, including calls to the same server; the initial product does not serialize every server by default.
- Cancellation and shutdown propagate through the SDK request signal and runtime generation. A non-responsive subprocess is terminated as a container or equivalent isolation unit after a bounded grace period. Because a per-user runtime may serve several runs, terminating that generation may fail sibling calls/runs for the same user and trigger one clean restart; this simple generation-wide failure mode is accepted. State-changing calls are not automatically retried after an ambiguous crash.
- Grant revocation, server disablement, revision activation, static-configuration replacement, OAuth connection-revision replacement, and idle expiry prevent new run bindings and schedule affected sessions/runtimes for drain after accepted runs finish. Startup reconciliation removes orphaned runtime state.
- The runtime-generation fingerprint is the async fence. A late start or health result for an old configuration, revision, OAuth connection, or disabled preference cannot mark the current server `Ready`. Turning a server off excludes it from newly accepted runs and prewarming immediately; the complete tool loop of every already accepted run, including later rounds and calls, continues through its recorded `McpRunBinding` and is not synchronously revoked underneath the run.

### Provider-neutral background and parallel tool loop

- MCP servers are an AIQSA tool source and executor, not a provider-specific feature. Discovery produces canonical AIQSA tool definitions; every provider adapter only serializes those definitions, parses provider tool calls, appends results, and describes model/provider capabilities. The MCP transport and credentials never depend on which LLM provider selected a tool.
- AIQSA executes its MCPs itself and exposes them to providers as client-executed function tools. OpenAI's provider-hosted `type: "mcp"` path is not used initially because it would bypass AIQSA's local stdio runtime, per-user sessions, credential ownership, and provider-neutral executor.
- The existing provider-tool loop is generalized rather than replaced by a workflow engine. The current Perplexity executor and MCP executors register behind the existing `ToolExecutor`/`ProviderToolBridge` contracts, and one extracted `continueToolLoop` function is called from both live execution and run recovery. Its logical checkpoint phases are `provider_running -> tools_pending -> tools_running -> provider_running -> completed|failed|cancelled`; the loop may repeat for multiple tool rounds.
- Effective capabilities are computed for the exact adapter, model, route, and active hosted/client tool combination and include at least `toolCalling`, `parallelToolCalls`, `nativeBackground`, and `backgroundStreaming`. These flags extend the existing `ProviderModel.capabilities` JSON rather than creating MCP-specific capability tables or a second provider interface. Unsupported combinations fail preflight rather than silently disabling MCP or changing a selected control. The user-selectable durable `Background` control is available only when `nativeBackground` is effective; an ordinary foreground request may survive a browser disconnect while the process remains alive but is not advertised as crash-recoverable background work.
- Only the current tool-loop checkpoint is mutable. `ModelRun.toolLoopState` records its version, phase, round index, bounded provider continuation and provider cursor when required; the existing `ModelRun.providerResponseId` is the current native handle. Completed history and usage remain in existing ordered `ModelRunEvent` and `UsageEvent` rows, not a `ProviderRound` table. A provider round is resumable after process restart only when its native handle was persisted; a process-local request without one fails recovery actionably. A create request with an ambiguous outcome and no returned handle or provider idempotency guarantee is never automatically repeated. Checkpointed resumable runs are handed to the existing recovery path and excluded from the legacy boot-orphan failure sweep.
- OpenAI Responses uses its native Background mode for every model round when the user selected it. AIQSA persists the current response ID and, where exact stream resumption requires it, the current sequence cursor inside the one checkpoint, then polls or resumes it, accepts cancellation, and streams it only when the user selected Stream and `backgroundStreaming` is effective. Tool results start a new continuation round with Background mode preserved. MCP tools must not force `background` or `stream` to `false`. This follows OpenAI's documented [Background mode](https://developers.openai.com/api/docs/guides/background) and multi-step [function-calling](https://developers.openai.com/api/docs/guides/function-calling) contracts.
- Streaming events use the existing ordered run-event sequence. Text is rendered as a provisional assistant draft; if a round produces tool calls, AIQSA emits one persisted `message_reset` event before tool execution and never appends that preliminary text to the durable final assistant message. A round with no tool calls promotes its accumulated draft as the final answer. Per-token round tags and a separate draft/round table are unnecessary for reconnect reconstruction.
- A provider may return zero, one, or several tool calls in one round. AIQSA persists the batch before dispatch and executes calls through a small bounded `mapLimit`/`Promise.allSettled` helper; the initial default maximum is four active MCP calls per run and no scheduler class is introduced. Results are correlated by provider call ID, restored to the provider's original ordinal, and supplied together after the batch settles, independent of completion order. Failure of one call becomes that call's result and does not automatically cancel its siblings.
- AIQSA requests provider parallel tool calling when the effective capabilities support it. A provider limitation, including restrictions caused by mixing provider-hosted built-in tools with client-executed functions, may reduce a round's parallelism but does not turn MCP into a foreground-only or globally sequential feature.
- Durable `ModelRunToolCall` records are unique by run ID, round index, and provider call ID and store the original ordinal, runtime binding, namespaced tool identity, bounded arguments, state, timestamps, and the already normalized/redacted continuation result. These private records follow the run's ownership and retention rather than the administration audit log. A completed result is reused during recovery and a not-yet-started call may be claimed. A call left `running` across an application crash has an ambiguous external outcome, is not automatically repeated, and fails the run with an actionable unknown-result error rather than risking a duplicate side effect.
- Cancellation cancels the current provider background response where supported, stops undispatched calls, and best-effort cancels in-flight MCP calls. It does not claim rollback of an external side effect that already occurred.

This amends ADR 0005 only for runs with client-executed tools: the process-local abort registry remains the fast live cancellation path, while provider handles and tool-loop checkpoints make continuation recoverable where the effective provider supplies a resumable handle, without pretending that process-local calls or ambiguous external side effects are exactly-once.

Provider-specific code remains only where wire protocols differ: an adapter serializes canonical functions, parses streamed or non-streamed tool calls, appends results, and implements its existing native create/refresh/cancel lifecycle. OpenAI removes its current tool-triggered foreground/stream disabling; OpenRouter collects streamed tool-call deltas; Anthropic maps `tool_use` and `tool_result`. MCP sessions, grants, credentials and executors do not gain provider-specific variants when another LLM provider is added.

### Persistent user enablement and multi-server tool plans

- Grant, user preference, configuration readiness and runtime readiness are separate states. A grant makes an MCP server and its complete current valid tool inventory available to the user; it does not enable the server. A newly granted server is disabled for the user until that user explicitly enables it.
- Each user has a persistent enabled/disabled preference for every entitled MCP server. A newly granted server is initially disabled; choosing OAuth `Connect` is an explicit connect-to-enable action and successful OAuth settlement turns the preference on without a second toggle. Non-OAuth enablement requires the declared personal fields or shared values, while an OAuth-backed server requires its ready per-user connection. If an administrator later introduces a required slot, an OAuth connection expires, or a credential fails validation, the preference remains enabled but configuration readiness becomes `Needs setup` or `Reauthorization required`; the server is not usable for a new run until corrected. Loss of the final effective grant turns the stored preference off, blocks new run bindings and prewarming, and drains the runtime after already accepted run bindings finish, so a later re-grant does not silently reactivate it. Partial direct/group grant changes recompute the effective union and schedule drain only when the resulting access or runtime configuration changes. Disabling a server likewise preserves accepted-run bindings until terminal but does not by itself disconnect OAuth.
- Every accepted run automatically includes all current valid tools exposed by each enabled and granted server. AIQSA has no product-level one-MCP-per-run restriction and does not require the user to repeat MCP selection in each chat or run. Model/tool-schema/context incompatibility is an actionable preflight failure, not a reason to silently filter tools.
- The LLM receives namespaced tool definitions, not MCP endpoints or credentials. Run preparation copies into the existing immutable `ModelRun.normalizedRequest` the exact enabled server/revision identities, bounded complete canonical tool definitions, tool IDs and definition hashes. One `McpRunBinding` per involved server references the exact runtime generation and therefore the effective static/OAuth configuration without copying a secret or live runtime handle into the normalized request. The snapshot is never a wildcard over tools discovered after run acceptance.
- An enabled server that is not ready is never silently omitted. A run may wait for a bounded `Preparing tools` reconciliation while a server is queued or starting. If setup, authorization, startup, or health still fails, the LLM call does not begin and the UI identifies the affected servers with actionable connect/reconnect/retry/configure/disable choices.
- Provider-facing tool names use stable AIQSA namespaces so equal or provider-incompatible upstream names cannot collide. Inspection surfaces retain the original server and tool display names.
- Aggregate schema/context, enabled-server, tool-count, call-count, result-size, timeout, and concurrency limits are explicit shared application policy. The initial small-installation release may keep those bounds as reviewed constants rather than adding operator configuration for each one. The ADR 0007 run budget includes the exact provider-facing tool definitions plus retained tool-call/result transcript, not only chat text. The settings UI warns or prevents enabling a set that cannot fit known hard limits; a run fails actionably if its selected model or current schemas make the set invalid. Tools are not silently dropped.
- Enabling tools from several servers authorizes the model to use their results in one model context. The UI must disclose that conversation-derived arguments or one tool's output may influence a later call to another enabled server. A future sensitivity policy may forbid specific combinations without changing the general multi-server contract.

### UI ownership and evidence

- `Admin -> MCP servers` is the sole editor for server configuration, revisions, shared secrets, typed configuration-slot definitions, OAuth mode/discovery policy, validation connection, requested scopes, validation-time tool inventory, runtime/network behavior, health, update, best-effort rollback, reversible disablement, and confirmation-gated irreversible deletion. A tested draft exposes `Activate tested revision` only when it differs from the active revision; an already active tested revision is presented as active rather than as another available action. Activation presents a clear trust warning that the model may invoke every current or future valid tool exposed by that MCP and that local workloads have unrestricted outbound networking. Installation-wide health is distinct from per-user readiness; the admin UI may show aggregate states, the informational validation inventory, and sanitized per-user inventory/failure summaries but never renders personal values or OAuth tokens.
- Group MCP-server grants live with the existing admin run-access ownership. Direct-user MCP-server grants and personal-value grants live in user administration. There is no separate per-tool grant editor.
- An ordinary user's `Settings -> MCP & tools` surface lists only entitled installation-owned servers. Each entry shows its description and that user's current runtime-scoped tools, a persistent enable/disable control, friendly administrator-declared fields the user may fill, OAuth `Connect`/`Reconnect`/`Disconnect` actions where declared, a safe external workspace/account label, and current readiness with an actionable error when relevant. The user cannot edit endpoint, OAuth client, scope, connection, or launch details.
- User-facing readiness states distinguish at least `Disabled`, `Needs setup`, `Needs authorization`, `Authorizing`, `Queued`, `Starting`, `Ready`, `Restarting`, `Idle`, `Reauthorization required`, and `Unavailable`. These are derived labels, not one persisted eleven-state workflow: preference yields `Disabled`; slot validation yields `Needs setup`; OAuth flow/connection yields authorization states; the compact runtime state `starting | ready | failed | idle | stopping` plus its reason yields the remaining labels. They are polled or streamed into the UI; a successful OAuth callback may prove that activation or enablement settled, but it never substitutes for the separate runtime-readiness observation. An idle-evicted but enabled runtime is shown as idle/starting rather than as an unexplained failure and is prewarmed when authenticated presence resumes. The word `Active` is not overloaded across administrator revision state, user preference, authorization connection, and process health.
- Runtime evidence includes the desired runtime-generation reference, generation fingerprint, freshness timestamp, stable redacted error, retry time, and attempt state. A stale `Ready` observation never bypasses send-time binding validation.
- The composer or Run summary shows a compact read-only count such as `Tools: 3 MCP ready` and an issue indicator linking to `Settings -> MCP & tools`. MCP enablement is not edited separately for every run.
- Run inspection survives navigation and reconnect and distinguishes provider work from tool work, including compact states such as `Waiting for model` and `Running 2 tools`. Background mode, streaming, and cancellation remain available when the selected provider capabilities support them; MCP presence never silently turns those controls off.
- Assistant runs show compact inline tool activity by default, including live and persisted calls. A persisted `Show tool activity` user preference may hide only this inline presentation; it never changes the accepted run, provider request, tool dispatch, durable evidence, or the Details/Events surface. The compact row is expandable per round and call and identifies the MCP server/tool, state, duration and safe bounded argument/result previews, including understandable parallel and failed calls. It never renders raw unrestricted payloads, executable configuration, endpoints or credentials.
- Run Events show server/tool identity, status, duration, credential source (`shared`, `personal`, or `oauth`), safe external workspace/account identity where policy allows, stable errors, and bounded redacted previews. Administration surfaces retain immutable revisions plus current validation/runtime evidence, but the initial small-installation release does not add a separate administrator activity-log subsystem. Raw secrets, OAuth codes/tokens/verifiers, process environments, commands containing secrets, and unrestricted arguments/results are not evidence payloads.

This amends ADR 0011 by adding a compact read-only Tools summary and a default-on inline tool-activity presentation preference to the run surface while keeping persistent MCP enablement and personal configuration in user settings, preserving direct Model, Reasoning, and Search ownership, and keeping Details as inspection rather than next-run editing.

## Consequences

- The requested team-governed model is supported without ordinary-user server installation or configuration.
- Administrators can connect both remote and stdio/package-based MCP servers, but installing a local MCP remains an explicit trusted-code operation inside the isolated runtime boundary.
- Package updates become explicit and inspectable instead of silently following registry state. Local rollback is best-effort and unavailable after its materialized Docker image is lost; AIQSA reports that condition rather than pretending to reproduce the old artifact.
- Personal API keys remain part of the product contract without granting users command or environment-map editing. AIQSA stores personal and administrator/shared values with one dedicated AES-256-GCM installation key and exposes them only as write-only typed slots, but effective local values are intentionally duplicated in plaintext ToolHive workload state and Docker environment metadata for the lifetime of that state and potentially in prior storage until cleanup. This is acceptable only under the documented trusted-host boundary; a later ToolHive secret-reference provider is optional defense in depth rather than a prerequisite. In normal integration remote static and OAuth credentials remain in AIQSA's encrypted store/common SDK session and are not sent to or persisted by ToolHive, while the accepted Docker authority still means a compromised controller can inspect wider host state.
- Per-user OAuth makes hosted services such as Notion compatible with the team-governed catalog without sharing one administrator identity, but adds browser callback, client registration, encrypted token storage, atomic refresh rotation, revocation, external-account evidence, and reauthorization UX to the product contract.
- An MCP server is trusted as one unit. Every valid current or future tool it exposes is available under the server grant, including state-changing tools, with no built-in per-call approval. This keeps administration simple and makes careful server selection an explicit administrator responsibility.
- Multi-MCP runs are supported and require no repeated per-run selection, but large enabled tool catalogs consume provider context and runtime resources and therefore require visible limits and later may benefit from dynamic tool loading.
- MCP works in foreground and streaming runs and in durable background runs wherever the effective model/provider combination supplies a native resumable handle; OpenAI Background mode is an initial required case. One extracted provider-neutral `continueToolLoop` function plus a small JSON checkpoint and durable call rows executes batches with bounded parallelism, while provider adapters own only wire formats and their existing native background/resume handles. Adding a provider requires generic tool-calling support, not a new MCP integration or workflow engine.
- The official MCP SDK removes custom JSON-RPC, Streamable HTTP, session, notification, cancellation and OAuth-protocol implementations. AIQSA still owns policy, safe fetch, encrypted state, result normalization and durable LLM orchestration. ToolHive remains only the local workload lifecycle manager. Both dependencies are pinned and accessed through narrow wrappers.
- Asynchronous prewarming makes the common Send path fast, but requires one in-process reconciliation timer, derived recent-session activity, user-visible readiness, retry/backoff, and orphan cleanup. It does not introduce a background worker service, queue, jobs table, or presence-lease subsystem. Send-time readiness checks remain necessary for correctness.
- MCP calls remain tool artifacts, not search runs. The shared provider-neutral continuation loop owns bounded parallel tool batches and durable recovery; adapters own only provider wire formats and native background handles.
- The isolated runtime adds deployment and operations work. Optional MCP health must not make the core application readiness fail, and disabling MCP must leave the QSA application usable.
- The simple initial Compose topology accepts ToolHive's root-equivalent host-daemon authority, the application's transitive access to it over a private unauthenticated TCP API, ordinary MCP outbound networking, and plaintext local environment transport as explicit trusted-infrastructure tradeoffs. A broker, Unix socket/OIDC, rootless separation, controlled egress, and per-workload resource ceilings are optional later hardening rather than initial blockers.

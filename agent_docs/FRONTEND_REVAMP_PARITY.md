# Frontend Revamp Parity Ledger

Updated: 2026-07-26

## Purpose And Authority

This is a temporary implementation ledger for replacing the current frontend presentation in place. It is not a product contract, architecture contract, design-system supplement, roadmap, or source of new product scope. It records where each already-approved capability and state must land, what evidence must prove the cutover, and when the legacy renderer may be retired.

The contract scope is **locked** by `CRITICAL_INVARIANTS.md`, accepted ADRs, `FRONTEND.md`, `DESIGN_SYSTEM.md`, the owning backend/security contracts, and the existing runtime behavior. `Locked` is a scope note, not an implementation status. If this ledger conflicts with an owning contract, fix this ledger. Product decisions must be made in the owning contract or ADR first and only then reflected here.

The revamp must replace presentation at the existing routes. It must not create a permanent `/v2`, a classic/new preference, duplicate API clients, duplicate stores, parallel server state, or invented product destinations. In particular:

- Research Chat remains `/`.
- Auth remains `/login` and its existing proof/outcome query modes.
- Public read-only snapshots remain `/s/[shareToken]`.
- Control Center remains `/admin` and preserves the existing `section` aliases.
- `Run receipt` is a new presentation of existing run-profile/model/search/tool/citation/reasoning/usage evidence. It is not a new backend resource or a third Details tab.
- Provider Quick setup is the approved Personal setup orchestration inside Providers. Advanced configuration and Run profiles remain inside the real Providers destination.
- Control Center navigation groups are presentation hierarchy, not plans, licenses, resources, or new routes.

All implementation rows start as `Planned`. Existing legacy tests are regression inputs, not proof that a replacement slice is verified.

## Status Legend

| Status | Meaning |
| --- | --- |
| `Planned` | Destination, owner, states, and required proof are identified, but the replacement has not been proven as the default presentation. |
| `In progress` | A replacement slice is being integrated against existing owners; legacy presentation remains reachable or parity evidence is incomplete. |
| `Verified` | The replacement is default at the existing route, applicable component and browser evidence passes, responsive/privacy checks are complete, and the replaced renderer is safe to remove. |

## Evidence Rules

- `Legacy owner` names the current behavioral/state owner and the presentation used to discover parity. It does not require preserving its markup or component boundaries.
- `New destination` names only an approved existing product destination or a presentation surface inside it. It does not reserve a new URL.
- `Evidence` describes the artifact required before changing a row to `Verified`: a replacement renderer/adapter, explicit state proof, and where applicable direct visual inspection.
- `Test` names the current regression suites to retain or adapt. New tests should be added only where a real replacement risk is not already observable.
- A row may be `Verified` only after the old and new renderers are not simultaneously owning the same production state.
- WCAG conformance and dedicated accessibility work are excluded from this revamp and from every cutover gate. Do not require screen-reader or forced-colors remediation, keyboard-only parity, formal focus-management proof, contrast thresholds, live-region audits, or dedicated accessibility tests as parity evidence. Existing semantics and keyboard behavior may remain through reused controls and incidental regression tests, but they do not block or certify a replacement slice.

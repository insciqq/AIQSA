# BACKEND API — UPLOADS AND SHARES

Owner: Server API contract maintainers
Scope: Observable upload, attachment, object settlement, anonymous-share creation, read, expiry, and revocation transitions.
Read when: Changing upload/attachment routes, processing/settlement outcomes, share creation/read/revocation/expiry, or snapshot projection.
Code owners: `lib/server/uploads/`, upload routes, share handlers/repositories, and public snapshot projection.
Not owned here: Storage threat controls, auth onboarding, chats/runs, or frontend share composition.

## Uploads And Shares

- Upload authenticates before body consumption, acquires a non-queueing process-local permit, and byte-bounds the complete multipart envelope before platform parsing. It validates ownership context, file size, extension/type, and magic bytes or text shape, settles the private object, then atomically creates a `processing` attachment plus its durable job; it does not parse inside the request. A filename must fit in 255 UTF-8 bytes, contain no path, NUL, CR, or LF separator, and have a nonempty basename before its supported terminal extension; bare extension names such as `.txt` fail as `unsupported_type`, while hidden names such as `.notes.txt` remain valid. Upload validation and parser routing share this filename rule so no accepted document can fail deterministically only at the later routing step. Stable overflow/busy outcomes are `413 file_too_large` and `429 upload_busy`, permits release on every path, stored MIME derives from the validated extension/type pair, and the response omits checksum/storage-key data. The accepted document set is the existing text/HTML/JSON/CSV/Markdown set plus DOCX, XLSX, PPTX, DOC, RTF, and ODT.
- A process-local coordinator is only a wake-up mechanism for the database queue. Workers claim due `AttachmentProcessingJob` rows with skip-locked leases, heartbeat long parser calls, verify settled size/checksum before parsing, and atomically publish `ready` or `failed` only while holding the lease. Transient storage/parser availability failures receive a bounded processing retry. A successful extraction instead keeps its normalized result for bounded ready-write retries under the same lease; a persistence exception never becomes a processing failure, and exhausted writes leave the job intact for lease-expiry recovery rather than publishing `failed` or scheduling a parser rerun. Restart or lease expiry safely resumes durable work. Docling/Tika own structured document extraction, while stopped/unavailable sidecars cause the local bounded PDF fallback and leave sidecar-only formats failed with a bounded stable `processingErrorCode`. Failed unattached rows may be retried through the owner-authorized attachment route; status/retry responses expose only the authenticated composer projection.
- Run creation and regeneration reject any selected non-`ready` row as `409 attachment_not_ready`, then the link transaction repeats `status = ready` in its compare-and-set. They return `413 attachment_count_limit_exceeded`, `413 attachment_materialization_limit_exceeded`, or `413 attachment_encoded_size_limit_exceeded` when one run exceeds its effective attachment boundary, `409 attachment_object_size_mismatch` when stored bytes contradict settled metadata, and sanitized `503 attachment_object_read_failed` when private object storage cannot be read. These responses may include only safe copy plus numeric `limits` and `actual`; attachment ids, filenames, storage keys, content, raw storage failures, and encodings are excluded. The authenticated catalog optionally projects `attachmentLimits.maxCount`, `maxMaterializedBytes`, and `maxEncodedBytes`; concurrency remains server-only and server admission remains authoritative for stale clients.
- Object keys are unique per upload. If row creation fails after object storage, a durable cleanup job is staged before immediate best-effort deletion; failed cleanup remains retryable.
- Public shares are immutable sanitized snapshots. The token is hashed for lookup; create/read/revoke never exposes live private state. Missing, invalid, expired, or revoked tokens share one generic unavailable response.
- Public API/page reads reauthorize against the repository on every request, are force-dynamic, use private no-store and noindex/noarchive policy, and never cache revocation behind the framework or an intermediary. Hosted-answer native Gemini live-only grounded answers cannot be shared as placeholder content.

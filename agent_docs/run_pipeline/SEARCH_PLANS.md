# RUN PIPELINE — SEARCH PLANS

Owner: Run pipeline maintainers
Scope: Provider-neutral Search choices, route planning, hosted/client execution, safe Sources/citations, recovery checkpoints, and Search retention semantics.
Read when: Changing Search options, route assignment, hosted/client Search, query-only execution, Sources/citations, budgets, recovery, or Search persistence.
Code owners: `lib/server/search/`, Search admission, provider Search adapters, and provider-neutral tool-loop execution.
Not owned here: Core non-Search run stages, frontend Search controls, provider-specific wire facts, or public sharing.

## Search Plans And Integrations

- Search is an explicit per-run plan. Its ordered `optionIds` contain zero to three current Search options and its mode is `all_selected` or `model_choice`. An empty plan is Off; `search-disabled` remains only the compatibility/default representation of Off and is never treated as an engine invocation.
- Send/regenerate requests carry the effective `searchPlan`, a separate preferred Search plan/source intent, and the per-model `controlDefaults` snapshot. The bounded compatibility decoder still accepts an old singleton `searchStrategy` and normalizes it to one option. Admission validates the effective plan against the selected model and the personal preference against readiness/entitlement independently. After validation, the backend commits the full preference and guarded run graph together before provider execution; it never persists a model-clamped subset, and a rejected run changes neither graph nor defaults.
- One optimistic-versioned installation `SearchPolicy` recommends an ordered plan for users whose `UserSettings.defaultSearchPlan` is null. The accessible portion is inherited dynamically and grants no entitlement. A non-null empty user plan is explicit Off, a non-empty plan is personal, and `Use organization default` returns to inheritance without copying the current recommendation.
- Every non-Off `SearchOption` is one user-visible source owned by exactly one provider connection; the connectionless `search-disabled` compatibility sentinel continues to represent Off without invoking an engine. The official OpenAI connection and every custom OpenAI-like connection therefore remain distinct sources. Physical hosted/query-only `SearchStrategy` routes are control-plane implementation details and never separate Composer or administrator choices. Eligible provider setup publishes configuration-backed immutable route revisions without a provider Search request; an optional diagnostic may record current connectivity but never unlock or disable the route. Archive removes the logical option and its routes from future catalogs without rewriting grants, defaults, accepted bindings, executions, or history.
- Admission resolves every selected source as one deterministic complete physical-route assignment. It considers only active typed routes belonging to that exact logical source and prefers same-connection hosted execution when that preference preserves the whole requested plan. Otherwise it uses the source's ready exact query-only route. Catalog exposure and admission resolve the current user's effective technical model, credential, active versions, and current availability check rather than comparing them with credential proof stored in a global Search revision. Credential rotation and different personal/group/default credentials therefore need no global re-probe, while every accepted run still pins its exact authority. It never substitutes another connection, key, endpoint, Search option, model, or provider when the exact source lacks a complete valid assignment. The ordinary catalog, Composer, preferences, policy, and grants use the logical option id as the user-choice identity; no physical route or revision id crosses those choice surfaces. Immutable run bindings additionally retain the admitted physical route, revision, and technical provider binding.
- `all_selected` requires a client route for every selected source, exposes one provider-neutral search action, and concurrently invokes every engine with the same bounded generated query. `model_choice` exposes each selected client engine separately and may retain at most one provider-hosted route only when that hosted protocol can coexist with every client Search/MCP tool in the answer request. A singleton same-connection hosted source keeps its existing behavior in either logical mode. If no complete assignment satisfies these constraints, admission rejects the plan without dropping a source or rewriting the user's preference.
- Every client-search invocation receives only one strictly validated bounded generated query plus reviewed server-owned result/timeout/routing/execution parameters. It never receives branch messages, original user content, system/developer prompts, provider tool messages, attachment ids, filenames, bytes, or extracted document text. Its query-only adapter does not inherit Composer or answer-model defaults: each immutable Search revision owns that source's output budget, reasoning policy, and per-answer invocation cap, while legacy revisions normalize to 4,096 output tokens, the lowest explicitly advertised reasoning effort, and two invocations without a migration or provider probe. Model-choice usage tracks each source independently; a fan-out invocation consumes one allowance from every participating source. Empty, malformed, extra-property, oversized, and over-budget calls fail closed without an engine call or Search execution row. Attachments never restrict Search selection, admission, or execution; this is a permanent product rule and must not be reintroduced as a disclosure-consent gate. Combining them does not broaden the query-only request shape: attachment ids, names, bytes, and extracted text remain unrepresentable to the client Search adapter.
- Fan-out runs concurrently with per-engine timeouts and caller cancellation. The immutable Search revision owns a 5-second to 15-minute engine deadline and new integrations default to 5 minutes. Each accepted technical provider binding separately owns its connection/model response deadline; the effective client-engine ceiling is the earlier of those two explicit snapshotted budgets. Admin shows both values and the result, while the accepted private execution checkpoint retains the effective millisecond values only when recovery or accounting consumes them. Successful findings are merged deterministically by plan order and engine-local rank, safe normalized URLs are deduplicated while retaining every contributing option/rank, and no semantic relevance score is invented. Partial success keeps successful sources plus per-engine warnings; total failure returns an explicit search/tool error and never calls an unselected fallback.
- Each actual client-engine call creates one separately attributable `SearchRun` with the minimum fields needed for deterministic continuation, citation reconstruction, stable errors, and accounting: exact option/revision/invocation identity, a bounded query only when replay or attribution requires it, canonical grounded findings, normalized safe citation sources, duration, status, and reported usage. Request previews and provider-operation traces are not product data and are not persisted solely for inspection. Every client adapter supplies findings and sources directly; common code never treats recursive URL discovery from an arbitrary provider body as source authority. Findings retain at most 48 KiB of UTF-8 per engine, and an incomplete response may retain only an allowlisted status/reason plus already reported usage—never the raw provider event or body. The canonical settled result is stored once and provider-facing tool content is derived from it for foreground continuation or recovery, so a completed call is not repeated. The complete durable tool result remains within 256 KiB; if an otherwise-valid result cannot fit, that engine becomes an attributable `search_result_too_large` error with usage rather than failing the answer run. Merely selecting an option or rejecting an over-budget call creates no execution. Hosted provider activity may emit transient normalized lifecycle events, but no post-hoc operation timeline is a client contract.
- `openai-native-web-search` is the canonical logical id for the official OpenAI Search source; the legacy `openai-provider-web-search` id is accepted only at bounded compatibility/migration boundaries and canonicalized to it. Official OpenAI Quick setup creates the parent plus same-source hosted and cross-provider query-only routes directly from the reviewed Responses `nativeSearch` declaration. It performs no paid Search request and creates no second user-visible option.
- `gemini-google-search` is one logical Google Search source with hosted and
  query-only physical routes. Eligible setup publishes its configuration-backed
  client revision against one exact active native Gemini deployment without a
  paid Search probe; normalized grounded findings and safe citations may return
  to any admitted tool-capable answer model. [Provider-neutral client Search](../backend/providers/CLIENT_SEARCH.md)
  owns the unary request mapping and terminal grounding proof.
- `anthropic-web-search` is one logical Anthropic source with the same hosted/query-only shape. Eligible official Anthropic setup publishes both configuration-backed routes without a paid Search probe. Both pin basic direct `web_search_20250305` with a three-use ceiling. Hosted execution is limited to a same-connection answer without app/MCP client tools; coexistence and cross-provider answers use the exact Anthropic technical model through a non-streaming query-only call. The normalized client execution retains the bounded cumulative `web_search_requests` count as provider usage when reported, never the surrounding provider payload. Provider `pause_turn` may replay its complete opaque response only in a three-continuation live loop; encrypted replay fields are never durable, settled query-only calls reuse the normal private checkpoint, and an interrupted ambiguous call is not repeated automatically.
- A custom OpenAI-like Responses connection with explicitly declared `web_search` creates its own connection-scoped logical OpenAI Search source and configuration-evidenced hosted/query-only routes, including explicitly tested private/local no-auth Responses connections. A query-only request receives only the validated generated query under the ordinary client-Search privacy, timeout, recovery, current-credential, and binding rules, whether the selected answer is OpenAI, Anthropic, Gemini, or another tool-capable model.
- The hosted Gemini-answer route keeps its strict native grounding fence: once
  an actual hosted search begins, the adapter withholds answer text until
  non-empty Search Suggestions pass the parser; that hosted grounded answer,
  Suggestions, Links, search result/signature data, and provider markup remain
  live-only, non-shareable, and non-replayable. When another Search source or
  client/MCP function must coexist, admission selects the query-only Gemini
  route instead. That client route uses Suggestions and native call/result
  signatures only transiently as terminal grounding proof, then discards them
  and retains/passes only bounded findings, normalized citations, the minimum
  recovery facts, and reported usage. On 2026-08-03 the operator accepted the
  provider-contract/compliance risk of passing those normalized Grounded
  Results to another selected answer provider and retaining them as ordinary
  client-Search results for this self-hosted/dev-only installation; that
  decision does not relax query-only disclosure, secret, markup, attachment, or
  raw-payload boundaries.
- Perplexity search runs only through an explicit selected client integration using the reviewed OpenRouter/Perplexity protocol. Its provider model may be explicitly technical-only: it then remains valid for Search credential/check resolution and immutable Search bindings without answer entitlement, but is absent from answer-model catalogs and rejected by answer admission. The technical model, credential precedence, routing/privacy defaults, output bounds, and active revision are server-authoritative; no hostname, display-name, or upstream model-id special case exists.
- Expose enabled, dependency-ready, entitled options once through the backend catalog and list compatibility separately on each answer model. A hosted option with no entitled available compatible answer model and a client option with no available compatible technical model are absent even when a stale active revision exists. A model switch marks retained incompatible preferences unavailable and excludes them only from the effective run plan; direct stale requests fail closed.
- Store ordinary citations/annotations/search result metadata as response artifacts. Citation URLs pass through the shared link-safety helper before persistence/read-back/rendering; unsafe schemes render inertly. Citations from hosted-answer Gemini grounding are the deliberate transient exception; citations normalized by the query-only Gemini Search adapter follow the ordinary client-Search citation and retention contract.
- Live presentation may distinguish Search off, pending, active, partial, failed, and complete only while that state is actionable. After settlement, the answer exposes only safe inline citations and the simple Sources projection when sources exist. Search attempts, generated queries, provider operations, route identities, ordinals, timing panels, and per-engine traces are not returned for a post-hoc disclosure. [Messages and Markdown](../frontend/MESSAGES_AND_MARKDOWN.md) owns citation and Sources placement; recovery owners consume private settled checkpoints directly.

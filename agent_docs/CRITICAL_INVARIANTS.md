# CRITICAL_INVARIANTS

Owner: Safety and durable product semantics
Scope: Cross-cutting rules whose violation can cause data loss, security/privacy exposure, incompatible persisted state, destructive verification, or a key run semantic change.

This is the mandatory short safety read. Scoped documents retain normative force only for their non-derivable product, safety, and operations constraints and are indexed by `INDEX.md`. Exact current implementation comes from code, schemas, migrations, and tests; product direction belongs in `PRODUCT_PRINCIPLES.md`, and durable UI semantics in `FRONTEND.md`.

## Data And Product Semantics

1. Provider, model, prompt, Search, Knowledge, Assistant, and parameter changes affect future messages only. Accepted historical turns, runs, bindings, user-visible outputs, and recovery-critical checkpoints are immutable except through an explicitly owned lifecycle transition.
2. A chat is a message DAG. Existing content with descendants is not edited in place, edits create branches, regeneration creates a sibling assistant through the run pipeline, and the visible branch derives from `activeLeafMessageId`.
3. Assistant messages use `queued`, `streaming`, `complete`, `cancelled`, or `error`; model runs additionally use private non-dispatchable `preparing` and provider-background `in_progress`. Completion, cancellation, preparation settlement, and recovered failure use guarded persistence so only one terminal writer wins.
4. Usage and cost derive from persisted provider-reported accounting data, never UI text length or placeholder prices. Browser run reads expose only the fields needed for lifecycle reconciliation and user-visible outputs. Repository objects, normalized requests, provider previews, internal event histories, retrieval internals, and tool traces are not client contracts merely because they exist in storage.
5. Provider, model, prompt, Search, Knowledge, Assistant, and run controls are resolved from the current user's server-filtered catalog and revalidated at admission. The browser cannot grant entitlement, select hidden configuration, or silently substitute an unavailable target.
6. `Share (anonymously)` creates a sanitized immutable snapshot, never access to live private chat state. Each read is dynamically repository-authorized and non-cacheable; its high-entropy bearer token plus expiry/revocation is authorization, while crawler directives are defense in depth.
7. Uploads and attachments remain private. Logs, internal events, operational records, previews, and public snapshots cannot expose attachment URLs, ids, filenames, bytes, extracted text, or storage keys outside an explicitly reviewed boundary.
8. An Assistant is a declarative execution profile with append-only immutable revisions. Assistant runs resolve the currently authorized revision server-side, record the exact `assistantId`/`assistantRevisionId` with the accepted run, and never trust a client-expanded copy of the governed controls. Publication pins exact revisions, grants no provider/model/Search/MCP/Knowledge entitlement, and admin status grants no access to private Assistants; invisible and nonexistent Assistants share one privacy-neutral response, and unavailable saved dependencies fail closed without substitution. Ordinary no-Assistant runs receive the code-owned standard-chat baseline rendered server-side with a recorded bounded time-zone fact; the browser cannot replace it.
9. Knowledge Bases are private retrieval resources. Base/document names, originals, normalized text, chunks, vectors, queries, focused requests, evidence manifests, private retrieval records, and citations remain private unless an authenticated answer projection deliberately exposes a safe citation label. Admin status grants no access to a private base, and invisible and nonexistent bases share one response. A Source is owner-scoped reusable identity with immutable Versions and immutable ready Profile artifacts; a Base is soft-removable membership and retrieval scope. Publication authorizes live future use while accepted bindings retain the exact content revision, vector generation, and immutable snapshot of ready Source Version/artifact evidence. Membership removal, Source replacement, and Profile changes affect future snapshots only. Equal checksums never imply one Source, and V1 reconciliation exposes aggregate counts rather than private identity or content. Public shares strip every private Knowledge artifact while preserving the generated answer text. An installation-owned immutable Knowledge Profile revision authorizes only the exact indexing/query-embedding destination; ordinary request fields never grant authority over that destination, and activation discloses the decision. Existing legacy generations keep their exact user-authority profile identity until explicitly reprocessed. New runs expose only strict `search_knowledge({ query })` inside the ordinary Search/MCP-compatible tool loop; accepted calls recheck scope and egress before external I/O, while historical focused runs remain read/recovery-only. Final Knowledge citations fail closed unless a completed persisted result and provider-running checkpoint prove that the exact result was delivered before synthesis. Ordinary management projects current files, readiness, and product actions only; it never exposes processing profiles, revisions/generations, chunk/vector details, Knowledge queries, evidence, or raw failures, and actionable failures use Reprocess plus an opaque support reference.
10. A Project is a shared tenant aggregate and a scoped entitlement source only inside itself for resources explicitly delegated or published to it. Its chats, attachments, Memory, shares, audit, and accepted run evidence belong to the Project; user/group RBAC is enforced server-side and every Project retains a direct active Owner. Active Project resources are available to current Contributor, Manager, and Owner roles through one canonical Project authority, independent of each initiator's personal grants, and never enter personal catalogs merely because of Project membership. Project models and Search use installation/shared credentials, Project MCP uses shared/no-auth configuration, and Project runs never consume personal credentials, Memory, history, unpublished Skills, OAuth identity, or personal MCP values. Membership never follows from a resource, and access/configuration drift before external dispatch fails closed.
11. Personal Memory mutation authority remains fail-closed to exact direct-current-user evidence and exact owned targets. Memory read admission is independent: every eligible non-empty ordinary answer retains a locally secret-redacted original query and deterministic local retrieval, while unavailable or invalid control, embedding, sorting, or aggregation may only degrade optional signals and cannot mint a mutation or hide already admitted evidence. Memory Safety Lite redacts recognized exact secret spans before every Memory derivative/provider/index/debug boundary, retains meaningful safe remainder, treats generic high entropy as audit-only, and never requires a semantic safety provider. Temporary, Project, disabled, owner, source, lifecycle, generation, deletion, exclusion, and safety fences remain hard failures.

## Security And Server Boundaries

1. Provider SDK/API calls stay behind server adapters. Untrusted route, provider, tool, and file input is authenticated where required, validated, and bounded before storage mutation or external I/O.
2. Private resources require server-side authentication, ownership, and entitlement checks at the operation boundary even when the browser already filtered their projection.
3. Raw user/provider request or response bodies are not ordinary logs and are not durably persisted unless a narrower reviewed contract proves they are required for execution, recovery, side-effect safety, security, or accounting. A generic debug or inspection use is not sufficient justification.
4. Upload handling validates size, extension/type, magic bytes or text shape, processing bounds, ownership, and storage settlement server-side.
5. Public snapshots strip raw provider payloads, private attachment data, secrets, internal run ids, and private user/group metadata.
6. Secrets, credential envelopes, password/database URLs, OAuth material, bearer tokens, and private operator notes never enter source control, AIQSA application logs, the supported structured access log, client contracts, previews, internal events, analytics, or public shares. One accepted deployment exception is limited to exceptional operator-controlled Nginx error diagnostics, where a public-share request path may contain its bearer token; those diagnostics are sensitive capability-bearing material and grant no exception for normal access logs, application logs, authorization headers, provider/MCP/session credentials, or any other token surface.

## Repository And Verification Safety

1. Never run destructive development, test, migration, prune, or browser workflows against the default persistent installation or an operator-designated data set. Only the explicit disposable development topology may be reset or polluted.
2. Completion moves task files from `agent_docs/tasks/queue/` to the ignored local `agent_docs/tasks/archive/`; operator parking moves reconciled unfinished tasks to `agent_docs/tasks/drafts/`, which is outside ledger selection and dependency resolution. Archive size never blocks validation or completion, and the harness never prunes, rotates, or overwrites archived tasks automatically. Cleanup happens only on an explicit operator request. Queued, parked, and archived task instances must never be forced into public Git, release source trees, or images.
3. Real-provider smokes require current operator-provided keys, the smallest scoped context/output, sanitized verification output, and the provider-specific permission in `TESTING.md`; deterministic fakes remain the default.
4. External dependency-security checks follow `SECURITY.md`; do not apply breaking or destructive remediation merely because an automated command proposes it.
